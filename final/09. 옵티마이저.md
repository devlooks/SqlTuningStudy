    - 규칙에 따라 실행계획 선택

  - 비용기반 옵티마이저

    - 비용 작은것 선택 실행
   
  - 최적화 목표
    - 전체 처리 속도 최적화 -> 결과 집합 끝까지 읽는것 전제로 처리 /*+ all_rows */
    - 최초응답속도 최적화 -> 결과 집합 일부 읽다 멈추는것 전제로 처리 /*+ first_row */
   
  - 옵티마이저 판단에 영향 요소
    - 연산자 형태
    - 옵티마이징 팩터 : 인덱스, IOT, 클러스터링, 파티셔닝 등..
    - DBMS 제약 설정 : PK, FK, Check, Not Null 등..
    - 옵티마이저 힌트 : 옵티마이저 판단 보다, 옵티마이저 힌트 우선(명령어)
    - 통계정보 : CBO의 모든 판단 -> 통계정보 기반
    - 옵티마이저 관련 파라미터
    - DBMS 버젼과 종류
   
  - 옵티마이저 한계
    - 옵티마이징 팩터의 부족 : 인덱스, IOT, 클러스터링, 파티셔닝 등..)
    - 통계정보의 부정합성 : 100% 정확 통계 현실적 불가능
    - 바인드 변수 사용시 균등 분포 가정
      - 바인드 변수 사용시, 데이터 균등 분포 가능, 비용계산
    - 비현실적 가정
      - ex) single과 Multi 를 같은 비용으로 평가
    - 규칙 의존 CBO
      - 비용기반도 규칙에 의존 함
    - 하드웨어의 특정
   
  - 통계 정보를 이용한 비용 계산 원리
    - 테이블 통계 : 전체 레코드, 총블록, 빈블록 수, 한행당 평균 크기 등..
    - 인덱스 통계 : 인덱스 높이 리프블록수, 클러스터링 팩터, 인덱스 레코드 수
    - 컬럼 통계 : 값의 수, 최저값, 최고 값, 밀도, null 값 개수, 컬럼 히스토그램
    - 시스템 통계: cpu 속도, 평균I/O, 초당 I/O 처리량
    - 선택도 -> 카디널리티 -> 비용 -> 액세스 방식, 조인순서, 조인 방법등 결정
      - 선택도 : 1/NDV
      - 카디널리티 : 선택도 / 총 로우 -> 총 로우 * 선택도 = num_rows/num_distinct
    - 히스토그램
      - 도수분포, 높이 균형, 상위 도수붐포, 하이브리드
        - 도수분포 : 값별 빈도수
        - 높이 균현 : 컬럼의 값이 많을 수록 버킷 할당이 어려움
       
    - 바인드변수 사용 -> 히스토그램 사용 X
   
    - 비용
      - 인덱스 경우 테이블 액세스 비용
        - 비용 = blevel (- 수직) + (리프블록 수 x 유효 인덱스 선택도) ( - 수평)+ (클러스터링 팩터 * 유효테이블선택도) (- table 랜덤 액세스)
        - blevel -> 브런치 레벨  
        - 클러스터링 팩터 -> 데이터가 모여있는 정도  
        - 유효 인덱스 선택도 -> 레코드 찾기 우해 스캔예상 비율 -> 곧 방문 리프블록 비율  
        - 유효 테이블 선택도 -> 최종 테이블 방문 예상 비율  
       
      - Full Scan  
        - 순차적으로 읽어 발생 I/O Call 횟수로 계산  
        - 총 블록수를 Multi Block I/O 단위로 나눈만큼 I/O Call 발생  
       
SQL 공유 및 재사용
  - 소프트 파싱 : SQL 실행 계획을 캐시에서 찾음 -> 실행 단계
  - 하드 파싱 : SQL 실행 계획을 캐시에서 찾지 못함 -> 최적화 과정 -> 실행 단게
  - 라이브러리 캐시 : 실행계획 저장 (해시구조로 관리)
  - SQL 공유, 재사용의 이유
    - 최적화 -> 무거운 작업
    - 조인순서
    - 스캔 방법
    - 통계정보 다시 등..

  - 실행 계획 공유 조건
    - 문접 오류 / 의미상 오류 검사
    - 해시함수 -> 해시값 -> 라이브러리 캐시내 해시버킷
    - 해시 버킷 연결된 엔트리를 차례로 스캔 -> SQL 문장 조회
    - SQL 문장 찾기 -> 저장 실행계획 바로 실행
    - SQL 문장 찾지 X -> 최적화 수행
    - 최적화 후 실행 계획 해시 버킷에 연결
    - 최적화 실행계획으로 실행

    - SQL 찾는 키값 -> SQL 문장 -> 하나라도 변경시, hard Parsing

바인드 변수 사용

  - 하나의 프로시저 공유 -> 반복 재사용
  - 라이브러리 캐시에 캐싱 -> 입력 값만 바인딩 -> 바로 실행
    - 하드파싱시 실행계획 -> Misses in library cache during parse : 1
  - 파싱소요시간, 메모리 사용량 줄임, CPU / 메모리 사용율을 줄임
    - 동접자 높을수록 효과가 좋음
  - 바인드 변수 사용 안하는 경우
    - 배치, DW, OLAP -> Long Running 쿼리
    - 컬럼값 종류 -> 소수
   
  - 바인드 변수 사용 권장 -> OLTP
  - 바인드 변수 -> 상수화 -> 문제 발생 가능성이 높음
  - 바인드 변수 사용시 주의 사항
    - 최적화된 실행계획에 변수만 바꿔사용
    - 옵티마이저 컬럼 데이터 균일 가정
    - 바인드 변수 보다 상수 사용이 유리 할 수 있음
   
  - 부작용 극복
    - 바인드 변수 Peeking/snifing
    - 적응형 커서 공유 (Adaptive Cursor Sharing) -> 변수 값 분포에 따라 실행 계획 사용
