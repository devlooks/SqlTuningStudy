1. 인덱스 기본 원리
   - 루트/브랜치 블록
     - 하위 노드 데이터 값 범위
     - 키 값에 해당 블록 찾는데 필요한 주소 정보
   - 리프 블록
     - 인덱스 키값 + 테이블 레코드 ROWID -> 키 값이 동일시, ROWID 기준 정렬 -> 양방향 연결 리스트
   - Oracle : 인덱스 구성 컬럼 모두 null -> 인덱스 저장 X -> 인덱스 구성컬럼 하나라도 null X -> 인덱스 저장
   - SQL Server : 인ㄷ게스 구성 컬럼 모두 null -> 인덱스 저장
   - null 값 -> Oracle 맨뒤 SQL Server 맨앞
  
2. 인덱스 탐색
   - 수직 탐색 : 루트 -> 리프
   - 수평 탐색 : 좌 -> 우, 우 -> 좌로 이동
  
3. 스캔 방식
   - Index Range Scan : 수직 + 수평(범위) 탐색
     - 항상 빠르지 않다.
     - 선두 컬럼이 조건절에 사용
     - 인덱스 없는 상태에서 인덱스 사용 강제하면 -> Index Full Scan
     - Index Range Scan -> Sort 연산 생략 가능
     - Index Full Scan
       - 수직 탐색이 아니라 인덱스 리프블록을 처음부터 끝까지 수평 탐색
       - 최적 인덱스가 없을 경우 차선으로 사용
       - 테이블 면적보다 작음으로 풀스캔에 비해선 효용성이 있음(결과집합이 적을 경우)
  
     - 인덱스를 이용한 Sort 연산 대체
       - 등치 조건 컬럼 다음 order by 컬럼을 으로 인덱스를 구성한다.
         
   - Index Unique Scan
     - SQL Server -> Oracle의 Range Scan, Unique Scan, -> Index Seek
    
   - Index Skip Scan
     - 레코드 포함 가능성 있는 하위 블록 골라서 액세스
     - 조건절에 빠진 인덱스 선두 컬럼 Distinct Value의 갯수를가 적을 때  
       후행 컬럼의 Distinct Value 개수가 많을 수록 유용
     - In-list -> In-list 내부 값이 적어야 한다
       (Skip Scan 과 비슷함, 단, 반복 수직 탐색 -> 비효율 가능성이 높다)

    - Index Fast Full Scan
      - Multi Block Read 방식
      - 병렬 가능
      - 세그먼트 단위(전체) 스캔
      - 순서 보장X
      - 인덱스 포함 컬럼으로 만 조회

    - Index Range Scan Decending
      - min/max 값 찾을때
      - index_desc
     
4. 인덱스 종류

   - B*Tree 인덱스
     - Unbalanced Index -> B*Tree에선 발생 하지 않음
     - Index Skew -> 인덱스 엔트리 왼쪽/오른쪽 치우치는 현상
       - 다시 채워질때 까지 인덱스 효율이 떨어진다.
       - SQL Server 에선 발생 X -> 정리 로직이 있음
       - Index Sparse : 인덱스 밀도 떨어짐
         - 지원진 자리에 새로운 값 입력 안함 재사용도 안함
         - 레코드 건수 일정 -> 공간 사용량 증가 현상
       - 인덱스 재생성
         - 인덱스 분할 자주 발생, DML 성능은 떨어짐
         - 인덱스 재생성 시간이 늘어남
         - 인덱스 분할시 경합이 높음
         - 인덱스 높이 증가(반복 액세스 인덱스 높이 증가)
         - 대량 delete 후 다시 레코드 입력 까지 오래 걸림
         - 레코드 수 일정 -> 인덱스 계속 커짐
        
   - 비트맵 인덱스
     - Null 도 저장
     - 칼럼의 Distinct Value가 적을때 사용 -> 저장 효율이 높음
     - 인덱스가 여러개 필요한 대용량 테이블에 유용
     - 단독으로 쓰임새는 별로
     - 대용량 데이터 검색 성능 향상 -> 효과
     - lock에 의한 DML 부하가 높음
    
   - 함수기반 인덱스
     - 인덱스에 함수 포함 구성
     - 부하 발생 가능성이 높음
    
   - 리버스 키 인덱스
     - 리버스 함수에서 반환된값 저장
     - ex) create index idx_name on table_ex(reverse(col1));
     - 등치만 조회 가능
     - 부등호, 범위 like 조회로 사용 못함
    
   - 클러스터 인덱스 : 1:M구조
     - ex) create cluster c_deptno# (deptno number(2)) index;
     - ex) create index i_deptno# on cluster c_deptno#;
     - 또는
     - ex) create table emp cluster c_deptno#(deptno) as select * from scott.emp;
     - 클러스터에 도달, 시퀀셜 방식으로 스캔 -> 넓은 범위 검색시 유리
     - 새로운 값 자주 입력 하게되면 -> 클러스터키 지정 하지 않는게 좋음
    
   - 클러스터형 인덱스와 IOT
     - 클러스터형 인덱스와 IOT
     - 별도의 테이블 생성하지 않음 -> 인덱스 리프페이지에 모든행 저장 -> 인덱스 분할 할수록 DML 부하가 높아짐
     - 일반적인 힙구조 -> 랜덤 Insert 방식
     - 클러스터형 인덱스 -> 정렬 유지 데이터 삽입(insert 성능이 떨어짐) -> 테이블마다 하나만 생성 
     - 넓은 범위 조회에 유리 ( 같은값 레코드끼리 100% 정렬)
     - Sql Server -> 인덱스 중복 가능
     - 넓은 범위 주로 검색
     - 크기 작고 NL 반복 룩업 테이블
     - 칼럼수 적고 로우수 많은 테이블에 추천
     - 데이터 입력 조회 패턴이 다른 테이블
    
5. 인덱스 튜닝 기초
     - 범위 스캔이 불가능 하거나 인덱스 사용하지 않을 경우
       - 인덱스 선두 컬럼 편집
       - 부정형 비교
       - 인덱스 칼럼에 not null 제약, is null 이 아닌 조건식 하나라도 있거나, is null 조건에 대한 index scan 기능
       - 인덱스 칼럼 가공
       - 묵시적 형변환
         - 문자형/숫자형 -> 숫자형
         - 문자형/날짜형 -> 날짜형
         - 인덱스 컬럼 타입에 맞춰 조건 구성 해야됨.
