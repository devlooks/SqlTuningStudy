1. Oracle 구조
   - DB : 디스크에 저장된 데이터 집합(DataFile, Redo log, Control File ...)
   - 인승턴스 : SGA 공유 메모리 영역과 이를 액세스하는 프로세스 집합
     - 하나의 인스턴스 하나의 DB접근
     - RAC -> 여러 인스턴스 -> 하나의 DB접근
    
2. 프로세스
   - 서버프로세스 -> 각종 명렬 처리
     - 전용 서버방식 :
       - 연결 요청 -> listener -> 프로세스생성/연결요청상속 -> Server -> Resend 패킷전송  
         -> 사용자 -> 연결후 작업 요청 -> 처리후 결과 전송
       - Connection Pooling 기법 필수 사용
       - 서버 프로세스가 단, 하나의 사용자 프로세스를 위해 전용 서비스 제공
    - 공유 서버 방식 :
      - 미리 여러개의 서버 프로세스를 띄워 놓고 이를 공유/반복 재사용
      - 사용자 프로세스 -> Dispatcher -> 요청 큐 -> 서버(SGA - 처리) -> 응답큐
     
    - 백그라운드 프로세스
      |백그라운드 프로세스| 설명 |
      |---|---|
      |System Monitor(SMON)| 시스템 장애 발생 -> 인스턴스복구 / 익스텐스, 세그먼트 모니터링|
      |Process Monitor(PMON)| 이상 발생 프로세스 사용 리소스 복구 |
      |Database Writer(DBWn)| Dirty 버퍼 -> 데이터 파일 기록 |
      |Log Writer(LGWR)| 로그엔트리 버퍼 -> Redo 로그 파일 기록 |
      |Archiver(ARCn)| 꽉찬 Redo 로그 Archive 로그 디렉토리 백업 |
      |check point| 어디까지 기록 -> 컨트롤 파일/ 데이터 파일을 파일 헤더에 저장 <br>  -> 버퍼캐시/데이터파일이 동기화된 시점 기록 -> 인스턴스 복구용도로 사용 |
      |Recoverer(RECO)| 분산 트랜잭션 -> 발생 문제 해결|

3. 데이터 저장 구조
   - 블록 (=페이지)
     - 오라클 -> 블록 -> 2,4,8,16,32kb
     - SQL Server > 페이지 -> 8kb
     - 읽을때 레코드 속한 블록(페이지 전ㅊ네 읽음)
    
   - 익스텐트
     - 공간 할단 단위 (TS로 부터)
     - 서로 인접 안함
     - 오라클 -> 종류 다양, SQL Server -> 8개 페이지 익스텐트 사용(64kb)
     - 오라클 -> 익스텐트에 속한 모든 블록 -> 단일 오브젝트 사용
     - SQL Server
       - 두개 이상 오브젝트가 나누어 사용
       - 균일 익스텐트 -> 단일 오브젝트 사용
       - 혼합 익스텐트 -> 여러 오브젝트 나눠 사용(64kb 넘으면 균일 익스텐트 사용)

    - 세그먼트
      - 테이블, 인덱스, Undo 저장 공간 필요로 하는 DB 오브젝트
      - 기본 : 오브젝트와 세그먼트 1:1 관계, 파티션과 세그먼트 -> 1:M 관계

    - 테이블 스페이스
      - 테이블 스페이스 -> 세그먼트를 담는 컨테이너
      - 여러 데이터 파일로 구성
        TS -< Seg -< Extent -< Block
              |      |
              DataFile

    - 임시 데이터 파일
      - 메모리 공간 부족 -> 중간 결과집합 저장 용도
     
    - 로그 파일
      - DB 모든 변경 사항 기록 -> Redo 로그 (Oracle), 트랜잭션 로그(SQL Server)
      - 데이터 블록 기록 -> Random I/O 방식 (느림)
      - 로그 기록 -> Append 방식 (빠름) -> 동기화 (배치)
      - Fast Commit : Redo 로그 믿고 빠르게 커밋
      - Online Redo 로그
        - 인스턴스 비정상 종료 -> 데이터 유식 대비 -> Online Redo 로그 사용(Oracle
        - 최소 두개 이상 파일 구성 -> log Switching(Round-Robin) (꽉차면 교체)
      - Archived(=offline) Redo 로그 - 미디어 복구 목적
     
4. 메모리 구조
   - SGA : DBMS  공동 사용 캐시영역 (DB버퍼, 공유풀, 로그버퍼 등.., Large 풀, 자바풀)
     - 액세스 직렬화 메커니즘 : 래치, 버퍼 lock, 라이브러리 캐시, Lock/pin
    
   - PGA : 데이터 정렬 세션, 커서에 관한 상태 정보 저장용도
   - 버퍼 캐시 : 데이터 파일로 부터 읽어들인 데이터 블록 담는 캐시
     - 데이터 변경 캐시 기록, 주기적 데이터 파일 동기화(DBWn)
     - 버퍼 블록 상태 -> Free, Dirty, Pinned(작업중)
     - LRU 알고리즘 : 버퍼관리 알고리즘 (least recently used)

   - 공유 풀
     - 딕셔너리 캐시 / 라이브러리 캐시로 구성
     - 딕셔너리 캐시 : 메타정보(테이블, 인덱스, TS,DataFile, Seg, Extent, User, 제약 조건 등)
     - 라이브러리 캐시 : 수행 SQL, 실행계획, 저장 프로시저 저장해두는 캐시영역
    
   - 로그 버퍼
     - 로그 엔트리를 우선 로그 버퍼에 저장 -> 파일에 기록
     - Write Ahead logging
       - Dirty 버퍼 디스크에 기록전에 로그엔트리를 먼저 로그파일에 기록
     - log force at commit
       - 커밋 시점에는 로그 파일에 기록 해야함
     - Fast Commit
       - 로그파일 믿고 Commit 완료

    - PGA :
      - UGA : 공유 서버방식 -> 프로세스와 세션간 1:M 관계
      - CGA : Call이 진행되는 동안, 필요데이터 담는 공간
        - Parse, Excute, Fetch Call 등 매법 CGA 할당
        - Recursive Call 발생 -> 각 Call 마다 CGA 할당
      - Sort Area : 소트 오퍼레이션시, 공간 부족 -> chunk 단위로 할당
        - sort_area_size(9i 이전)
        - workarea_size_policy = auto -> oracle 자동 사이즈 결정(9i이후)
        - PGA -> Excute -> sort area CGA에 할당
        - 최종 결과 집합 출력 전 -> Sort Area -> UGA에 할당


5. SQL 처리 과정
   - 구조 / 집합/ 선언
   - 처리 과정
     - Parser -> Optimizer -> Row-Source Generator -> SQL Engine(실행
     - Parser : 문법 판단
     - Optimizer
       - Query Transformer : SQL 표준형태
       - Estimator : 실행 계획 총 비용
       - Plan Generator : 실행 계획 생성
     - Row-Source Generator : 코드형태 포멧팅

   - SQL 옵티마이저
     - 후보군 실행계획, 실행계획 예상 비용, 최저비용 실행계획 선택
    
   - 옵티마이저 힌트 무시
     - 문법적 안 맞게 기술
     - 의미 없이 히트 기술
     - 잘못된 참조 사용
     - 논리적으로 불가능 엑세스 경로
     - 명령어 취급함
    
6. 데이터 베이스 I/O 메커니즘

   - 블록 단위 I/O
     - 데이터 파일에서 DB 버퍼캐시로 블록 적재
     - 데이터 파일에서 블록을 직접 읽고 쓸때
     - 버퍼캐시에서 블록을 읽고 쓸때
     - 버퍼 캐시에서 변경 블록 다시 데이터 파일에 쓸때
    
   - 메모리 I/O VS 디스크 I/O
     - 속도 : 디스크 보다 메모리가 더 빠름
       - 물리 I/O 필요시 -> 프로세스 -> 시스템에 I/O Call -> 잠시 대기 상태 빠짐
       - 디스크 I/O 경합이 높아짐 -> 대기시간도 길어짐

   - 버퍼 캐시 히트율(BCHR)
     - 전체 읽은 블록중 메모리 버퍼 캐시에서 찾은 비율
     - (버퍼 캐시 블록 수 / 총읽은 블록 수) * 100
         (query + current) - disk / (query + current)

   - 네트워크, 파일시스템 캐시가 I/O 효율에 미치는 영향
     - 네트워크 전송량을 줄임 -> 논리 블록 요청 횟수 줄임

   - Sequential I/O vs Random I/O
     - Sequential I/O : 논리적 또는 물리적 순서 차례대로
     - Random I/O : 한건을 읽기 위해 한블록 씩 접근
     - 튜닝 핵심
       - 시퀀셜 액세스 비중을 늘리고, 랜덤 엑세스 비중을 낮춰야함
       - 랜덤 액세스 발생량 줄리기 - 인덱스 변경
      
    - Single Block VS Multi Block I/O
      - Single Block I/O
        - 한번의 I/O Call -> 하나의 데이터 블록 메모리 적재
      - Multi Block I/O
        - 인접한 블록을 같이 읽어 메모리 적재
        - 익스텐트 범위 넘기지 않음
        - I/O Call 줄임
       
    - I/O 효율화 원리
      - 최소 블록만 읽도록 SQL 작성
        - 반복 접근 줄이고 (테이블 반복 스캔(같은범위 X))
      - 최적의 옵티마이징 팩터
        - 전략적 인덱스
        - DBMS 제공 가능 : 인덱스, 파티션, 클러스터, 윈도우 함수 등..
        - 옵티마이저 모드(전체처리속도, 최초응답속도)
        - 통계정보
      - 옵티마이저 힌트 -> 액세스 경로 유도
