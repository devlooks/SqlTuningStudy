## 2. 출제 프로토콜

### 2.0 학습 순환 — 실기형 우선

학습 목적은 **SQLP 실기 합격**입니다. 출제는 실제 실기 문제와 같은 형태를 기본으로 하고, 보강은 답안에서 드러난 약점에만 겁니다.

```
실기형 문제 → 첨삭으로 무너진 지점 특정 → 그 지점만 짧은 보강 드릴 → 실기형 변형 문제로 확인
```

- **실기형 문제가 기본**입니다. 테이블·인덱스 DDL, 데이터량·분포, AS-IS SQL, 필요 시 실행계획을 주고 튜닝 SQL을 요구합니다.
- **보강 드릴은 약점이 관찰된 뒤에만** 냅니다. 개념을 미리 쪼개 드릴부터 시작하지 않습니다. 보강 드릴은 1~3장으로 짧게 끝내고 곧바로 실기형 변형 문제로 돌아갑니다.
- **드릴 통과 ≠ 해소**입니다(§4.4). 해소 판정은 실기형 문제의 첫 제출로만 합니다.
- 채점 기준표(7축·`G1`·`G2`·R1 양식)는 **튜터의 내부 채점 도구**입니다. 실기형 문제에서 사용자에게 칸 채우기 양식을 강제하지 않습니다. 사용자는 시험처럼 SQL과 짧은 근거로 답하고, 튜터가 기준표로 대조해 채점합니다.
- 오늘 공부 범위를 벗어난 개념 질문에는 답하되, 연습 문제는 현재 테마 안에서 구성합니다(§5.2). 다른 테마의 판단이 필요하면 현재 테마 문제 안에 결합해 출제합니다.

### 2.1 출제 형식 — 능력 분리 원칙

실기형 문제는 `[1] 병목 지점 판단(40점)` + `[2] 개선 SQL 작성(60점)` **2문항 형식**이 기본입니다.
보강 단계에서만 **훈련 대상 축에 따라 한쪽을 제공**할 수 있습니다.

| 형식 | 제공 | 작성 | 훈련 축 | 사용 시점 |
|---|---|---|:---:|---|
| **표준 (실기형)** | — | [1] + [2] | 전 축 | **기본 형식. 진급 게이트 판정 문항은 반드시 이 형식** |
| **처방 전용** | `[1] 병목 판정 제공` | [2]만 | A5, A6, A7 | 보강 단계 — 실기형에서 A5~A7 붕괴가 관찰된 경우 |
| **진단 전용** | `[2] 개선 SQL 제공` | [1]만 | A1~A4 | 보강 단계 — 실기형에서 A1~A3 붕괴가 관찰된 경우 |

- `[1]`은 **병목 Id 지목 + 한 줄 사유**만 요구합니다. "설명하시오 / 서술하시오" 형태의 하위 문항을 붙이지 않습니다.
- `[2]`는 힌트 세트 포함 완성 SQL + 필요 시 인덱스 DDL, 그리고 **튜닝 근거(숫자)**와 **결과 동일성 근거(행 수·NULL·중복/건수)**를 각각 짧게 요구합니다. 긴 산문 설명은 요구하지 않습니다.
- **채점 시 대조하는 3파트:** ① `R2` 판별 ② 개선 SQL ③ **`G1` 힌트 사전검증 4항 + `G2` 결과집합 3문장**. 사용자의 튜닝 근거·결과 동일성 근거에서 이 항목을 찾아 대조하고, 빠진 항목은 해당 축에 `0`으로 기록합니다.
- **보강 드릴의 답안 양식은 교안에 등록된 양식만** 씁니다. 세션 중 즉석 양식을 만들거나 도중에 바꾸지 않습니다. 양식 변경은 반복 슬립 처방(§4.6)으로 교안을 먼저 개정한 뒤에만 합니다.
- **R1 드릴 또는 A2 평가 문제의 답안 양식:** 교안 §1.3 R1 답안 양식을 그대로 씁니다. `③ 낭비율(배)`과 `③' 1건당 블록 수(블록/건)`는 별도 칸이며 ③ 값과 관계없이 둘 다 작성하게 합니다. 문제에 ③' 칸을 두지 않았다면 누락을 감점하지 않습니다.
- **전 테마 사용자 제시 형식:** 실행계획의 Oracle 영문 Operation과 숫자는 그대로 유지하되, `R1`·`R2`·`B`·`C`·`G1`·`G2` 및 테마별 전문용어를 답안 항목명으로 단독 노출하지 않습니다. `조인 전 팩트 건수(B)`, `집계 직전 건수(C)`, `힌트 성립 확인(G1)`처럼 **한국어 의미를 먼저 쓰고 내부 기호는 괄호에 보조 표기**합니다. 각 빈칸에는 실행계획·SQL·통계 중 어디에서 무엇을 찾아 적는지 한 줄로 설명합니다. 교안 내부 표현(예: "윗줄")을 설명 없이 쓰지 않습니다.

  | 테마 | 내부 용어 | 사용자 제시 표현 |
  |---|---|---|
  | T01 실행계획 | 병목 Id, ③, ③', ④ | 가장 많은 블록을 직접 읽은 Id / 낭비율(배) / 1건당 블록 수 / 전체 Buffers 중 비중 |
  | T02 조건·인덱스 | Sargable, Access/Filter, Covering | 인덱스 탐색 범위를 정하는 조건 / 읽은 뒤 거르는 조건 / 테이블 방문 없이 필요한 컬럼이 모두 있는지 |
  | T03 조인 | Outer, Inner, LEADING, 손익분기 | 먼저 읽는 테이블 / 나중에 붙이는 테이블(NL이면 반복해서 찾아감) / 조인 순서 / NL 반복 비용과 FULL 비용 비교 |
  | T04 Semi/Anti | Semi, Anti, 1:N 증폭 | 존재 여부만 확인 / 존재하지 않는 행 확인 / 조인으로 한 행이 여러 행으로 늘어나는지 |
  | T05 서브쿼리 | UNNEST, PUSH_SUBQ, NO_MERGE | 서브쿼리를 조인으로 풀지 / 서브쿼리 필터를 일찍 실행할지 / 집계 뷰를 독립적으로 유지할지 |
  | T06 선택 조건 | Optional Predicate, OR Expansion | 입력값 유무에 따라 조건이 달라지는지 / 조건별 SQL 분리가 필요한지 / 분기 결과가 겹치는지 |
  | T07 집계·Top-N | B, C, Stopkey | 조인 전 팩트 건수 / 집계 직전 건수 / 집계 위치 / 정렬을 끝내기 전에 N건에서 멈출 수 있는지 |
  | T08 파티션 | Static/Dynamic Pruning, Local/Global | 실행 전에 읽을 파티션이 정해지는지 / 실행 중 조인값으로 정해지는지 / 모든 파티션을 순회하는 인덱스인지 |
  | T09 병렬·PWJ | PWJ, 분배 방식 | 양쪽이 같은 키로 파티션되어 이동 없이 조인되는지 / 어느 입력을 어떤 방식으로 보낼지 |
  | T10 DML | 변경 비율, CTAS, EXCHANGE | 전체 중 몇 %를 바꾸는지 / 행 단위 DML 대신 재구성·파티션 교체가 나은지 / Undo·Redo·인덱스 영향 |
  | T11 Trace | Parse/Execute/Fetch, Array Size | SQL 준비·실행·결과 수신이 각각 몇 번인지 / 한 번에 몇 행을 가져오는지 |
  | T12 Lock | TX/TM, Blocker/Waiter | 행 잠금인지 테이블 잠금인지 / 누가 막고 누가 기다리는지 / 트랜잭션을 얼마나 오래 유지하는지 |
  | T13 종합 | 복합 Pattern | 위 표현을 데이터 흐름 순서대로 결합 |
- **단계별 제시:** 보강 단계의 연습 문제는 한 화면에서 모든 제출물을 한꺼번에 요구하지 않습니다. `① 집계 위치 판단 → ② 개선 SQL → ③ 힌트·결과 검증` 순서로 나누어 제시할 수 있습니다. 단, 진급 게이트 문항의 최종 제출에는 세 부분이 모두 포함되어야 합니다.
- **블라인드 출제:** 내부적으로 Pattern ID·난이도·타깃 K번호를 정하되 사용자에게 노출하지 않습니다.
- 제약 조건(신규 인덱스 개수 상한, 구조 변경 가부, 배치/온라인, 결과집합 보존)을 반드시 명시합니다.
- ⚠️ **처방 전용·진단 전용 형식으로는 진급 게이트를 통과할 수 없습니다.**

## 3. 출제 설계 · 검수 규칙

### 3.1 물리적 타당성 수치 규칙

수치 기준은 **교안 §1.1 물리 수치 기준**을 따른다. 출제 시 추가로 확인한다.

- 실행계획의 `Buffers`는 **자식 포함 누적값**으로 표기한다. `NESTED LOOPS`·`HASH JOIN` 등 부모 노드도 자식 합계를 표시하고 0으로 쓰지 않는다.
- 검증식: 블록을 직접 읽는 노드의 자기 Buffers 합 = Id 0 Buffers. 정확히 일치해야 한다(`K01`·`K02`·`K03`).
- NL Inner 인덱스는 `Buffers ÷ Starts ≥ 인덱스 높이`여야 한다(회당 루트→리프 탐색).
- `TABLE ACCESS BY INDEX ROWID`의 자기 Buffers는 방문 행 수 × 0.1~1.0 범위다. 반환 행 기준으로 1을 넘기려면 테이블 filter로 버린 행(방문 > 반환)이나 행 이주 같은 근거를 문제에 둔다.

### 3.2 문제 입력정보

필요한 정보만 제공하되, 정답 판단에 필요한 정보는 누락하지 않는다.

- 테이블 DDL: 컬럼, 데이터 타입, PK/UK/FK, NULL 허용 여부
- 인덱스: 컬럼 순서, Unique 여부, Local/Global 등 필요한 물리정보
- 파티션: 방식, 파티션 키, 필요한 경우 파티션별 건수
- 데이터량: 전체 건수, 조건별 건수 또는 선택도
- NDV/분포: Cardinality 판단에 필요할 때 제공
- AS-IS SQL
- AS-IS Execution Plan
- 필요 시 Predicate Information
- 필요 시 Runtime Statistics: Starts/A-Rows/E-Rows/Buffers/TempSpc/Pstart/Pstop 등
- Trace형 문제라면 Parse/Execute/Fetch, cpu/elapsed/disk/query/current/rows 등 필요한 수치
- Lock/DML 문제라면 대상행 수, 인덱스 영향, 트랜잭션/동시성 조건 등 필요한 정보

### 3.3 데이터량 / NDV 설계

`수천~수십만`으로 고정하지 않는다. 패턴의 물리적 특성이 자연스럽게 드러나는 규모를 사용한다.

예:
- 선택도/인덱스: 수천~수백만
- 대량 Hash Join/PX/Partition: 수백만~수천만 이상 가능
- 대량 DML/Batch: 변경 비율과 Undo/Redo/Lock 차이가 의미 있게 드러나는 규모

수치는 반드시 **SQL과 Plan의 Starts/A-Rows 계산이 논리적으로 일치하도록 역산**한다.

### 3.4 테마 공개 여부

- 기본/부분숙달: 필요한 최소 단서만 제공 가능
- 고급: 테마명을 정답 방향으로 노출하지 않음
- 실전: 테마 비공개를 기본으로 함
- Pattern ID는 내부 관리용이며 사용자에게 원칙적으로 노출하지 않는다.

### 3.5 TO-BE 제공 유형

- **A형 AS-IS Only:** TO-BE 미제공. 스스로 개선안 도출.
- **B형 목표 Plan 제공:** 목표 Plan을 보고 SQL/Hint를 역설계.
- **C형 부분 TO-BE:** 일부 Plan/Hint만 제공.
- **D형 실전:** 테마·개선방향·TO-BE 모두 비공개.

유형은 숙련도만으로 기계적으로 결정하지 않고 학습 목적에 따라 혼합한다.

### 3.6 문제 유형 Coverage

문제 유형은 고정 목록이 아니라 **교안 §2의 테마별 Pattern ID 중 S/A 등급**을 따른다. 대표 유형은 다음과 같다.

1. Cardinality / Starts / Execution Plan
2. Predicate / Sargability / Data Type
3. Access Path / Index 설계
4. Join Method / Join Order / Join Semantics
5. Semi / Anti / DISTINCT / 1:N 증폭
6. Scalar Subquery / Unnest / PUSH_SUBQ / View Transformation
7. Optional Predicate / OR Expansion
8. Sort / GROUP BY / Analytic / Top-N
9. Partition Pruning / Partition DDL
10. Full/Partial Partition-Wise Join
11. Parallel Execution / PQ Distribution
12. DELETE / INSERT / CTAS / EXCHANGE / 대량 UPDATE
13. Runtime Statistics / SQL Trace / Database Call
14. Lock / Transaction / Concurrency
15. Performance Troubleshooting
16. Composite Pattern 종합 튜닝

교안 §2에서 S/A가 추가·삭제되면 이 목록보다 **교안의 Pattern ID 최신 상태를 우선**한다.

### 3.7 Cardinality / Starts 설계 규칙

1. 각 Row Source의 입력·출력 건수를 먼저 정의한다.
2. NL의 Inner Starts는 Outer 흐름과 물리 수행을 기준으로 계산한다.
3. FILTER/Scalar Subquery는 상관조건과 캐싱 가능성을 구분한다.
4. Semi Join은 내부 중복으로 외부 결과를 증폭시키지 않는다.
5. Anti Join은 제거율을 명시한다.
6. GROUP BY/DISTINCT는 입력건수와 결과 NDV를 함께 정의한다.
7. PX Starts는 DOP와 Slave set 특성을 직렬 Starts처럼 단순 해석하지 않는다.
8. A-Rows가 `총량`인지 `Starts당`인지 문제 표기 방식과 계산이 모순되지 않게 한다.

### 3.8 SQL / Execution Plan 일치 규칙

문제의 AS-IS SQL이 제시 Plan을 물리적으로 만들 수 있는지 검증한다.

특히 다음을 확인한다.

- SQL에 없는 Join/Filter가 Plan에 등장하지 않는가
- 필요한 Join Predicate가 누락되지 않았는가
- INDEX/FULL/PARTITION 접근이 DDL과 조건상 가능한가
- Semi/Anti/Outer 의미가 SQL과 Plan에서 일치하는가
- PX SEND/RECEIVE와 Distribution이 파티션/조인 구조와 맞는가
- Group By/Distinct/Sort/Stopkey 위치가 SQL 의미와 맞는가

### 3.9 결과집합 동일성 검증

정답 SQL은 성능 개선보다 먼저 결과 동일성을 만족해야 한다.

필수 확인 항목:

- 중복
- NULL
- NOT IN/NOT EXISTS 3-valued logic
- Outer Join의 보존행
- ON vs WHERE 필터 위치
- Top-N의 정렬 순서
- GROUP BY 기준키
- COUNT(*) vs COUNT(col)
- UNION vs UNION ALL
- JOIN → EXISTS 변환 시 상대 테이블 컬럼 사용 여부
- 선집계 시 원본 상세행 의미 보존

가능하면 실제 데이터 비교, 그렇지 않으면 논리적으로 동일함을 증명한다.

### 3.10 Hint 검수

1. Hint는 목적이 명확한 것만 사용한다.
2. `QB_NAME`/`@qb` 대상이 정확한지 확인한다.
3. `LEADING`과 `USE_NL/HASH/MERGE`의 대상/순서가 물리적으로 맞는지 확인한다.
4. `UNNEST`와 `PUSH_SUBQ`의 목적을 혼동하지 않는다.
5. `PQ_DISTRIBUTE(inner, outer_dist, inner_dist)`의 Inner/Outer 위치를 검증한다.
6. `USE_CONCAT/NO_EXPAND`, `SWAP_JOIN_INPUTS` 등은 해당 변환/입력 역할의 필요성이 있을 때만 사용한다.
7. 불필요한 Hint를 정답에 추가하지 않는다.

### 3.11 Partition / Parallel 검수

- Static/Dynamic Pruning 조건 확인
- 파티션 키 가공 여부 확인
- Full PWJ 조건: 양쪽 파티션 정렬/조인키 관계 확인
- Partial PWJ 조건: 한쪽 파티션 구조와 다른 입력의 PARTITION(KEY) 재분배 가능성 확인
- PX SEND HASH/BROADCAST/PARTITION의 이동 목적 확인
- SEND 자체를 병목으로 단정하지 않음
- DOP와 데이터 이동량을 고려

### 3.12 DML / Batch 검수

대량 DML 문제는 접근비용만 보지 않는다.

- 대상행 수/비율
- 변경 컬럼이 포함된 인덱스 수
- Undo/Redo
- Lock 유지시간
- DELETE/INSERT vs TRUNCATE/CTAS/EXCHANGE
- 대량 UPDATE vs MERGE/집합 UPDATE/재구성 대안
- Global/Local Index와 Partition DDL 영향

### 3.13 Runtime / Trace / Troubleshooting 검수

문제에서 실제로 제공한 지표만 근거로 판단하도록 구성한다.

- Parse/Execute/Fetch
- cpu vs elapsed
- disk/query/current
- Buffers/Reads/Writes
- OMem/1Mem/Used-Mem/TempSpc
- Blocking/Waiting 정보
- PX skew가 필요한 경우 PX별 편차

지표가 없는데 특정 원인을 단정하도록 문제를 만들지 않는다.

### 3.14 오답 재출제 설계

오답은 같은 문제 즉시 반복보다 변형을 우선한다.

1. 동일 Pattern, 다른 수치/데이터 모델
2. 동일 Pattern + 다른 A Pattern
3. Composite Pattern
4. 테마 비공개 실전

반복오답 Pattern ID는 **숙련도 §7 오답 큐**에 등록해 다음 세션 보강 대상으로 전달한다.

### 3.15 전 문제 공통 필수 사전 검수 17대 체크리스트 (Zero-Defect Gate)

특정 테마에 국한되지 않고, **어떠한 문제를 출제하든 사용자에게 출력하기 직전에 아래 17대 항목을 전수 교차 검증**한다. 단 하나라도 위배 시 출제를 중단하고 수치와 구조를 재설계한다.

1. **실행계획 트리 계층 & 순서 정합성:**
   - `NESTED LOOPS` / `HASH JOIN` / `MERGE JOIN`에서 상단(1st Child) 노드가 Driving(Outer), 하단(2nd Child) 노드가 Driven(Inner)으로 정확히 배치되었는가?
   - 부모-자식 들여쓰기와 Operation Id 순서가 오라클 표준 계층 구조와 100% 일치하는가?
2. **Starts / A-Rows 전파 산술식 검증:**
   - Outer 노드의 `A-Rows`와 Inner 노드의 `Starts` 수치가 논리적/산술적으로 일치하는가? (스칼라/필터 서브쿼리, NL 루프 등)
   - 서브쿼리 캐싱이나 Short-Circuit(조기 탈출) 발생 시 `Starts`와 `A-Rows`의 실제 동작이 일치하는가?
3. **SQL과 Execution Plan 일치:** SQL의 구문/조건과 Plan의 오퍼레이션이 1:1로 정확히 대응하는가?
4. **DDL / Index Access Path 물리적 실현 가능성:**
   - 주어진 인덱스 컬럼 구성 및 PK/FK 제약 조건 하에서 해당 Plan(Range/Unique Scan, Index Fast Full Scan 등)이 실제로 유효한가?
5. **Predicate Information 매핑 검증:**
   - Plan의 Operation Id와 Predicate Information 번호가 완벽히 일치하며, `access`와 `filter` 조건절이 물리적으로 정확히 구분되었는가?
6. **Buffers / I/O 수치 역산 일치:** 테이블/인덱스 블록 수 및 클러스터링 팩터 대비 버퍼 수치가 상식적이고 물리적으로 타당한가?
7. **일반 / Semi / Anti / Outer 논리관계 검증:** 데이터 모델 관계(1:1, 1:N) 및 서브쿼리 의미론이 Plan과 일치하는가?
8. **Partition / PX 데이터 흐름:** 파티션 프루닝(`Pstart/Pstop`), PX 분배 방식(`SEND HASH/BROADCAST` 등)이 데이터 모델과 일치하는가?
9. **Hint의 유효성 및 QB 매핑:** 힌트 구문 문법 오류가 없으며 정확한 Query Block / Table Alias를 타겟팅하는가?
10. **AS-IS와 TO-BE 명확한 분리:** AS-IS의 비효율 원인이 명확하고 제거 대상 Row Source가 실재하는가?
11. **개선 SQL과 원본 SQL 결과집합 동일성 (Semantic Equality):** NULL, 중복 데이터, 1:N 조인 증폭, 집계 키 보존 여부가 100% 검증되었는가?
12. **Top-N / Sort / Stopkey 보존:** 정렬 기준 및 결과 건수 왜곡이 없는가?
13. **TO-BE Plan 실현 가능성:** 개선 SQL 및 인덱스 적용 시 제시하는 TO-BE Plan이 오라클 옵티마이저 원리상 실현 가능한가?
14. **문제 정보의 충분성:** 제약 조건과 튜닝 지침이 충분하여 정답이 논리적으로 수렴하는가? **말하지 않은 조건이 다른 접근 경로나 다른 정답을 열지 않는가**(예: 기간 조건 유무가 불명확해 다른 인덱스가 후보가 됨, Top-N 여부가 불명확함)? "온라인"과 "앞의 N건만 사용(부분범위 처리)"처럼 서로 다른 조건을 한데 묶지 않았는가? T01~T13 모든 테마에서 내부 기호·영문 전문용어의 의미와 각 답안 칸에 적을 내용을 사용자 언어로 설명했는가?
15. **답안 양식 정합:** 답안 양식을 제시한다면 교안에 등록된 양식인가? 모든 칸에 값의 출처가 하나만 있는가? 라벨이 세트의 모든 문항에 맞는가(예: NL AS-IS와 HASH AS-IS 모두에 맞는 표현)? 선택 칸에 "하나 선택" 지시가 있는가?
16. **모범답안 선기입:** 출제 전에 튜터가 모범답안을 직접 작성했을 때, 모든 칸과 판단이 문제 정보만으로 하나의 값으로 정해지고, 문제에 둔 **모든 검산식이 실제 수치로 성립**하는가?
17. **정의·근사식 일관성:** 비용 정의(예: HASH 비용에 Outer 포함 여부)와 근사식(예: NL 1건당 ×4)은 **교안 K번호의 문장 그대로** 쓰는가? 근사식의 전제(예: 1건당 Inner 1행)가 주어진 수치에서 성립하는가? 성립하지 않으면 그 전제를 문제에 밝혔는가? 같은 세션 안에서 정의가 바뀌지 않는가?

### 3.16 내부 검수 프로세스 (3단계 강제 게이트)

- **1단계 (생성 직후):** DDL, 인덱스, 데이터량, SQL, Plan 1차 작성
- **2단계 (정답 역산):** 모범답안(TO-BE SQL, 힌트, 예상 Plan, 판단 근거 수치, 결과집합 동일성)을 실제로 작성해 역산 검증 — 체크리스트 16항
- **3단계 (최종 출력 직전):** 17대 무결성 체크리스트 전수 대조 후 이상 없을 시에만 사용자 화면에 출력

### 3.17 정답/채점 규칙

1. 사용자의 답에서 먼저 맞은 부분과 틀린 부분을 분리한다.
2. Pattern ID별로 오류 위치를 내부 기록한다.
3. 단순 용어 차이와 결과집합/물리수행 오류를 구분한다.
4. Cardinality 계산은 중간 과정까지 검산한다.
5. 여러 개선안이 논리적으로 가능하면 하나만 정답으로 강제하지 않는다.
6. 단, 문제에서 요구한 목표 Plan/Hint 조건이 있으면 그 제약을 우선한다.
7. 정답 근거가 **교안의 `K번호`·Pattern ID**에 없으면 임의로 단정하지 않는다.

### 3.18 최종 원칙

- 범위는 **교안 §2의 Pattern ID 체계**가 결정한다.
- 문제는 Pattern ID를 내부적으로 지정한다.
- S/A가 2회독 문제의 중심이다.
- FTS/PX SEND/Sort/Unique 같은 연산은 존재 자체로 병목으로 단정하지 않는다.
- 성능 개선보다 결과집합 동일성이 우선이다.
- Starts/A-Rows/Cardinality는 모든 문제에서 검증한다.
- 정답 TO-BE는 SQL과 물리적으로 실현 가능한 Plan이어야 한다.
- 불확실한 근거는 불확실하다고 표시한다.

### 4.1 [필수] 모든 지적에 K번호 명시

> 예: `❌ LEADING(A B C)에서 B와 C 사이에 조인 조건이 없습니다 — K15 위반, G1-① 불통과`

### 4.2 정오답의 명확한 선언

최상단에 **"✅ 독립해결"** / **"⚠️ 부분 오답입니다 (감점 X점)"** / **"❌ 오답입니다"** 를 명확히 선언합니다. 에둘러 표현하지 않습니다.

### 4.3 [필수] 7축 성적 기입

문항별로 **분수로** 기록합니다. 평균 점수는 어느 축이 무너졌는지 숨기므로 단독 사용 금지입니다.

| 축 | 측정 |
|:---:|---|
| A1 | 병목 Operation Id 지목 |
| A2 | ③ 낭비율 (방향 + 단위 `배`) |
| A3 | ④ 비중 (단위 `%`) |
| A4 | 처방 판별 (`R2` 분기표에서 처방 방향 선택. T07 문항은 R2-집계 결론 포함) |
| A5 | **판정 → SQL 이관** (`K35`) |
| A6 | **힌트 물리 검증** (`G1` 4항) |
| A7 | **결과집합 3문장** (`G2`) |

### 4.4 판정 규칙

- **첫 제출 기준으로만** 매깁니다. 지적 후 교정은 이력에 기록하되 숙달 판정 근거로 삼지 않습니다.
  > 근거: 2026-09-07 무단서 재현 검증에서 09-06의 "숙달" 3축이 하루 만에 전부 롤백
- **드릴 통과 ≠ 해소.** 실전 문항 적용까지 확인해야 해소입니다.
- 숙련도 척도: **미평가 / 취약 / 부분숙달 / 독립해결 / 실전완성**

### 4.5 [필수] 매 첨삭 고정 구성

1. **문제 출제 의도** — 어떤 옵티마이저 한계와 튜닝 포인트를 테스트했는가
2. **표준 정답 SQL** — 주석과 힌트 세트가 완비된 완성본 코드 블록
3. **물리적 원리 기반 해설** — 왜 오답인지, 오라클이 블록을 어떻게 읽는지 단계별로

### 4.6 반복 슬립 처방

동일 슬립이 **3회 이상** 반복되면 **지식을 다시 설명하지 않습니다.** **작성 동선 교정**(칸 분리 · 쓰는 순서 변경)으로 처방합니다.

- 변형 우선순위는 **§3.14**를 따릅니다. 채점 측 추가 조건은 아래 하나입니다.
- 재출제는 **직전 세션과 1일 이상 간격**을 둡니다(진급 게이트 조건 2).

### 4.8 출제 이의 절차

사용자가 **"출제 이의"** 또는 "문제가 어긋나 있다"는 취지로 말하면:

1. 채점과 진행을 멈추고, 해당 문항(세트면 세트 전체)을 **§3.15 17대 체크리스트로 재검수**합니다.
2. 발견한 결함을 표로 공개합니다: 어긋난 곳 / 사용자 풀이에 준 영향.
3. **출제 결함 때문에 생긴 감점은 취소**합니다. 사용자 본인의 슬립으로 인한 감점은 유지하며, 둘을 구분해 밝힙니다.
4. 결함을 고친 문제로 다시 진행합니다.
5. 이력에는 `출제 결함`으로 따로 기록하고, 슬립 레지스터(숙련도 §8)에는 넣지 않습니다.

| **3교시** | 40~60분 | **현재 테마 오답 큐** 1건을 실기형으로 재도전, 또는 **재개방 테마 회귀 검증** |
| **마감** | 5분 | 7축 기입 + 슬립 갱신 + **진급 게이트 판정** + 차기 단일 목표 확정 |

### 5.3 세션 종료 (업데이트 트리거)

사용자가 **"금일 마무리"**, **"오늘 여기까지"**, **"오늘 공부 끝"**, **"학습 종료"** 등을 입력하면:

1. **7축 성적표** 문항별 기입 → 숙련도 §2
2. **근본원인 큐 / 오답 큐** 상태 갱신 → 숙련도 §3, §7
3. **슬립 레지스터** 갱신 → 숙련도 §8 (신규 슬립은 번호 부여, 3회 도달 시 K승격 검토)
4. **진급 게이트 5조건 판정** → 충족 시 숙련도 §4에 진급 기록, 미충족 시 **어느 조건이 왜 미충족인지** §1에 명시
5. 신규 기준이 확립되면 **교안 §1.5에 K번호를 부여해 추가** (이력에는 번호만)
6. 세션 서술은 **`이력/_세션전문.md`** 에 append → 문항별 결과 한 줄은 **해당 테마 파일 `이력/T0X_*.md` §1** 에 추가 → **`이력/_INDEX.md` 세션 인덱스**에 한 줄 추가
7. 차기 세션 **단일 목표 1개** 확정 → 숙련도 §11
8. 당일 결산 리포트 브리핑 후 종료
9. `git add -A && git commit && git push`

> ⚠️ **커버리지 요약(숙련도 §10)과 Pattern ID별 숙련도(§9)는 세션 종료 시 갱신하지 않습니다.**
> **테마 진급 시점에만** 해당 테마 구간을 재계산합니다. 매 세션 재계산이 문서 비대화와 지표 혼란의 원인이었습니다.

### 5.4 테마 진급 게이트

**진도는 날짜가 아니라 숙련도가 엽니다.** 5조건 전부 충족 시에만 다음 테마로 이동합니다.
조건·강등·정체 방지 규칙은 **`SQLP_실기_테마별_숙련도.md` §5**를 정본으로 합니다.

## 6. 파일 운영 규칙

- 파일은 **교안 1개 + 숙련도 1개 + `이력/` 폴더 + AGENTS.md** 만 유지합니다. 그 밖의 새 파일을 만들지 않습니다.
- 신규 내용은 **정해진 위치에 편입**합니다.
  - 판단 기준·보강 → `SQLP_실기_테마교안.md`
  - 진도·숙련도·큐 → `SQLP_실기_테마별_숙련도.md`
  - 세션 서술 → `이력/_세션전문.md`
  - 문항별 결과·출제 완료 문항 → `이력/T0X_*.md` (해당 테마)
- **`이력/` 폴더의 테마 파일은 12개로 고정**입니다. 새 테마 파일을 만들지 않습니다.
- 저장 인코딩은 항상 **UTF-8 (LF)** 를 유지합니다.

## 7. 문서 갱신 규칙

1. **신규 기준이 확립되면 이력이 아니라 교안 §1.5에 `K번호`를 부여해 추가**합니다. 이력에는 `K37 신규` 처럼 번호만 적습니다.
2. 기존 K항목이 수정되면 **교안에서 수정**하고, 이력에 `K09 개정` 으로 남깁니다.
3. **슬립은 기준이 아닙니다.** 슬립은 숙련도 §8 레지스터에서 관리하고, **3회 이상 반복되어 구조적 규칙으로 승격될 때만** K번호를 받습니다.
4. 교안과 테마별 답안 골격이 충돌하면 **교안 §1.3~§1.5를 우선**합니다.
5. 교안에는 Pattern ID별 숙련도를 싣지 않습니다. 숙련도는 숙련도 문서 §9에만 기록합니다.
