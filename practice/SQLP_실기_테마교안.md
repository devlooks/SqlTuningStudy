## 1.1 대원칙

> **기준보다 절차가 먼저다.** (2026-09-07 실증)
> 09-05에 확립한 8대 판단 기준은 **적용할 대상(병목 Id)을 못 찾으면 무용**이라는 것이 4문항 전패로 확인되었다.

> ⇒ 같은 오류가 3회 이상 반복되면 **지식을 다시 설명하지 말고 칸을 분리**한다.

> **힌트는 판단의 받아쓰기다.** 판단이 없으면 `LEADING`/`USE_NL`은 매번 새로 지어내는 추측이 되고, 같은 슬립이 반복된다. (→ K35)

## 1.2 답안 1문항 표준 동선

```
[R1] 실행계획 판독 5-STEP        →  병목 Id 확정 + ③낭비율 + ④비중
        ↓
```

**진단이 되는 것과 처방이 나오는 것은 별개**이므로, 세 구간을 각각 채점하고 각각 훈련한다.

## 1.3 루틴 (R) — 반드시 이 순서로 쓴다

### R1. 실행계획 판독 5-STEP

SQL을 보기 **전에** 실행계획 표만으로 수행한다.

| STEP | 쓰는 것 | 근거 기준 |
|:---:|---|---|
| ① | **Id 0의 A-Rows**를 종이 맨 위에 적는다 (= 목표 건수) | — |
| ② | **자기 Buffers 최대인 리프 Id**에 동그라미 (= 범인) | K01, K02, K03 |
| ③ | 범인 Id의 A-Rows와 ①의 A-Rows를 **윗줄에 나란히** 적고 나눈다 → **낭비율(`배`)** | K09, K10 |
| ④ | 범인의 자기 Buffers ÷ 전체 Buffers → **비중(`%`)** | K04 |
| ⑤ | 검산: 블록을 만지는 노드의 자기 Buffers를 **실제로 더해** 전체와 일치시킨다 | K03 |

**작성 동선 규칙 (필수):**
- ③을 쓸 때는 **Buffers 열을 손으로 덮는다.**
- ④를 쓸 때는 **A-Rows 열을 손으로 덮는다.**
- **단위가 곧 검산이다.** ③은 `배`, ④는 `%`. 단위가 안 맞으면 열을 잘못 본 것이다. (→ K10)

### R2. 처방 판별 — 집계 위치 B/C 3스텝

| STEP | 확정할 것 |
|:---:|---|
| ① | **팩트 테이블** = `SUM`/`COUNT` 대상 컬럼이 속한 테이블 |
| ② | **B** = 그 팩트 테이블 **액세스 노드의 A-Rows** |
| ③ | **C** = 최종 `GROUP BY` **바로 아래 노드의 A-Rows** (= 조인·필터를 모두 통과한 뒤 집계 직전 행 수) |
| ④ | **조인의 정체** 판정 — 붙이기인가 필터인가 (→ K21) |
| ⑤ | 결론: `B ≈ C` → **선집계** / `C`가 자릿수로 작음 → **후집계** |

> 판별 결과를 **한 줄로 적고 나서** SQL을 쓴다. 2026-09-10 최대 실패 원인은 판별 성공(3/4) 후 **SQL에 반영하지 못한 것**(1/4)이다. (→ K35)

## 1.4 게이트 (G) — 제출 전 통과 의무

### G1. 힌트 사전검증 4항

| # | 점검 | 불통과 시 증상 |
|:---:|---|---|
| ① | **LEADING 인접성** — 나열 순서에서 인접한 두 테이블 사이에 WHERE 조인 조건이 있는가 | 카티션 곱 (→ K15) |
| ② | **힌트 짝 정합성** — `PUSH_PRED`는 NL 전용. `USE_HASH`와 동시 사용 시 무효 | 힌트 상호 무효화 (→ K28) |
| ③ | **인덱스 실존** — 지정한 인덱스가 실제로 존재하는가. 신규 설계면 **선두 컬럼 = 조인키**인가 | 존재하지 않는 인덱스 지정 (→ K30) |
| ④ | **손익분기** — `NL 반복횟수 × 회당 블록수` **vs** `상대 FULL 블록수`를 **숫자로** 적었는가 | 감으로 조인 방식 선택 (→ K17, K18) |

> **작성 "중"에 채운다.** 2026-09-10에 4문항 중 3문항이 성립 불가능한 힌트였다(카티션 / 상호 모순 / 미존재 인덱스).
> 사후 검사로는 이미 늦다 — 힌트를 타이핑하는 순간 해당 항을 같이 적는다.

### G2. 결과집합 동일성 3문장

| # | 문장 |
|:---:|---|
| ① | **행 수** — 개선 후 행 수가 원본과 같은 근거 (조인 차수·세미 전환·집계 단위) |
| ② | **NULL** — OUTER 보존 여부, `SUM`은 NULL 무시 / `COUNT(*)`는 포함이라는 비대칭 처리 |
| ③ | **중복** — 증폭 제거 근거. `DISTINCT`를 뺐다면 **왜 더 이상 필요 없는지** (→ K29) |

> 🔴 **8주 연속 누락 중인 유일한 항목이며, 실제 사고(2026-09-07 결과집합 10,800 → 150,000건 파괴)가 발생한 항목이다.**
> 배점 여부와 무관하게 **답안 하단 고정 위치에 먼저 자리를 만들고** 시작한다.

## 1.5 판단 기준 K01~K36

### A. 실행계획 판독 (K01~K07)

| K | 기준 | 내용 |
|:---:|---|---|
| **K01** | Buffers 누적 규칙 | 부모 Buffers = 자기 것 + 자식 전부. 블록을 실제 읽는 것은 **테이블/인덱스를 만지는 리프 노드뿐**. 리프들의 합 = 전체 |
| **K02** | 블록 미접근 노드 | `HASH JOIN` / `NESTED LOOPS` / `SORT` / `GROUP BY` / `FILTER` / `UNION-ALL` / `PARTITION RANGE ALL` 은 자기 Buffers 0. **반복자·메모리 연산**이다 |
| **K03** | 검산 항 개수와 덧셈 | 항의 개수 = 블록을 만지는 노드의 개수. 항에 **부모 원본**이 섞이면 자식이 중복되어 반드시 초과한다. **실제로 더하지 않은 검산은 요식행위** |
| **K04** | 병목 후보 컷오프 | Buffers 비중 **5% 미만은 병목 후보에서 즉시 제외** |
| **K05** | 오퍼레이션 의미 판독 | `SORT AGGREGATE`는 정렬이 아니라 **집계**. 같은 레벨 형제 노드 + 그 Starts == 메인 A-Rows → **SELECT 절 스칼라 서브쿼리 반복** |
| **K06** | 파티션 프루닝 신호 | `Pstart 1 / Pstop N`(= 전체 파티션) → **프루닝 실패**. 파티션 키 조건 부재 또는 **가공**이 원인 |
| **K07** | 칸 분별 | **Starts는 Starts 칸에서 읽는다.** E-Rows(추정)와 A-Rows(실측)를 혼동하면 전 과정이 무너진다 |

### B. 병목 판정 (K08~K12)

| K | 기준 | 내용 |
|:---:|---|---|
| **K08** | 병목의 정의 | 비용이 큰 곳이 아니라 **낭비가 크면서 미룰 수 있는 곳**. 판정 질문은 **"나중에 해도 되는가?"** |
| **K09** | 병목의 두 유형 | ③ ≥ 1 → **행 낭비형**(`A-Rows ÷ Id0 A-Rows`). ③ < 1 → **블록 낭비형**으로 지표 전환(`③단계 보조지표 = Buffers ÷ A-Rows` = 1건당 블록수). **1 미만이 나왔다고 분자·분모를 뒤집지 않는다** |
| **K10** | ③·④ 상호검산 | ③이 1 근처인데 ④가 크면 둘 중 하나가 틀렸거나 블록 낭비형 전환이 빠진 것. **③은 `배`, ④는 `%`. 단위가 안 맞으면 열을 잘못 봤다** |
| **K11** | 반복 횟수 ≠ 병목 | **Starts가 크다고 범인이 아니다.** 판정은 순수 **자기 Buffers**로 한다 |
| **K12** | FULL ≠ 병목 | "FULL이면 병목"은 관성이다. 저비중 FTS는 **미끼**다. K04 컷오프를 먼저 적용한다 |

### C. 조인 순서 · 드라이빙 (K13~K16)

| K | 기준 | 내용 |
|:---:|---|---|
| **K13** | 드라이빙 선정 | 총 건수가 아니라 **필터 후 남는 건수**. 조건 없는 테이블은 후보가 아니다 |
| **K14** | 3순위 이후 순서 | 크기가 아니라 **도달 가능성** — 지금까지 읽은 것이 그 조인키를 갖고 있는가 |
| **K15** | LEADING 카티션 방지 | 나열 순서에서 **인접한 두 테이블 사이에 WHERE 조인 조건이 있어야 한다.** 허브 테이블(양쪽 연결)은 **가운데나 앞**에 배치 |
| **K16** | USE_NL 대상 지정 | `USE_NL`은 **inner(driven) 테이블**을 지정한다. **LEADING 1순위에 `USE_NL`을 걸지 않는다** |

### D. 조인 방식 (K17~K19)

| K | 기준 | 내용 |
|:---:|---|---|
| **K17** | 자릿수 비교법 | 나눗셈 폐기. `[바깥 건수]`와 `[안쪽 블록수]`를 나란히 적고 **자릿수만 비교**. 바깥이 1자리 이상 작으면 **NL**, 비슷하거나 크면 **HASH** |
| **K18** | 손익분기 정량식 | 손익분기 ≈ **안쪽 테이블 블록수 ÷ 4**. `FULL`은 반드시 **`USE_HASH`와 세트** |
| **K19** | 배치 vs 온라인 | 배치 = **전체범위**(HASH/FULL 정당). 온라인 = **부분범위**(NL + Stopkey) |

### E. 집계 위치 (K20~K24)

| K | 기준 | 내용 |
|:---:|---|---|
| **K20** | 선집계 판별 공식 | 집계 입력이 **조인 전 > 조인 후**면 **후집계**, **조인 전 < 조인 후**면 **선집계**. 조인이 건수를 줄이는지부터 센다 |
| **K21** | 조인의 정체 | **PK/UK 조인(1:1)은 절대 건수를 줄이지 않는다 = 「붙이기」 → 무조건 선집계 후보.** 「필터」인 조인만 후집계 |
| **K22** | 변환 가능 집계함수 | **`SUM`/`COUNT`/`MIN`/`MAX`만 선집계 ↔ 후집계 자유**(결합법칙). **`AVG`·`COUNT(DISTINCT)`는 2단 집계 시 결과 왜곡** |
| **K23** | 선집계 안전 조건 | 선집계 결과를 조인할 때 **조인 상대가 유일(PK/UK)해야 한다.** 아니면 증폭으로 `SUM` 중복 가산 |
| **K24** | 선집계 인라인뷰 골격 | 뷰의 `GROUP BY`에 **바깥 조인키를 반드시 포함**. 뷰는 `NO_MERGE`. 필터를 뷰 안으로 내릴 때 **지표가 소실되지 않는지** 확인(예: 상태코드를 뷰 WHERE로 내려 취소 지표 소실) |

### F. 서브쿼리 · 쿼리변환 (K25~K29)

| K | 기준 | 내용 |
|:---:|---|---|
| **K25** | UNNEST 시 LEADING 구성 | 평탄화하면 서브쿼리 테이블도 조인 대상이다. **`LEADING`에 서브쿼리 테이블을 반드시 포함**하고, 통상 **2순위**에 배치 |
| **K26** | 두 접근안 병기 | 필터 시점 제어 문제는 **① UNNEST + `NL_SJ` ② `NO_UNNEST` + `PUSH_SUBQ`** 두 안을 모두 제시하고 손익분기로 택일한다 |
| **K27** | NO_MERGE / PUSH_PRED 선택 | **줄이는 뷰면 `NO_MERGE`.** 뷰 **전체** 필요 → `USE_HASH` / 뷰 **일부만** 필요 → `PUSH_PRED` + `USE_NL` |
| **K28** | PUSH_PRED 짝 | `PUSH_PRED`는 **NL 전용**. `USE_HASH`와 함께 쓰면 무효화된다. 배치는 뷰 **바깥** 블록 + **뷰 별칭** |
| **K29** | DISTINCT 제거 순서 | ① 증폭 제거(일반 조인 → `EXISTS` 세미) → ② **그 결과로** `DISTINCT`가 불필요해진다. **순서를 바꾸면 결과가 깨진다** |

### G. 인덱스 설계 (K30~K33)

| K | 기준 | 내용 |
|:---:|---|---|
| **K30** | 선두 컬럼 분별 | NL의 inner(조인 통로) → **조인키 선두**. 단독 범위스캔 커버링 → **범위키 선두 + 집계 컬럼 포함**. "조인키 선두"는 공식이 아니라 **NL inner일 때의 결론** |
| **K31** | 커버링 사전 점검 | 그 테이블의 `SELECT`·`WHERE`·`GROUP BY` 컬럼이 **전부** 인덱스에 있는가. 없으면 **테이블 방문 횟수 = 인덱스가 뽑은 행 수** |
| **K32** | 스캔 방향 | ASC로 생성한 인덱스에 역순 정렬을 요구하면 `INDEX` 힌트로는 정렬이 생략되지 않는다. **`INDEX_DESC`** 를 쓴다 |
| **K33** | access vs filter | 필터가 **access**면 데이터 분포가 비용을 좌우하고, **filter**면 A-Rows 표시만 바뀐다(블록은 이미 읽었다) |

### H. 작성 규율 (K34~K36)

| K | 기준 | 내용 |
|:---:|---|---|
| **K34** | UNION ALL vs CASE WHEN | `SELECT` 문 개수 = 스캔 횟수. **액세스 경로가 갈리면 `UNION ALL`, 같으면 `CASE WHEN` 1회 집계** |
| **K35** | 판정 → SQL 이관 | **판별해서 도출한 결론을 SQL 구조에 반드시 반영한다.** "후집계"라고 써놓고 선집계 구조를 유지하면 [1]의 점수가 [2]로 이어지지 않는다. 제출 직전 **판정 문장과 SQL 구조를 나란히 놓고 대조** |
| **K36** | 구문 일관성 | 콤마 조인(전통)과 ANSI `JOIN` 구문을 **한 쿼리에서 혼용하지 않는다.** 문법 오류로 직결 |

## 1.8 출제경향 · 시험전략

### 1. 정보 신뢰도 기준

- **A:** 공식 발표/공식 문서 또는 프로젝트에서 공식근거로 검증된 내용
- **B:** 복수 자료와 Oracle 원리가 교차 지지하는 내용
- **C:** 제한적 사례 또는 간접 근거
- **D:** 추정. 단독 출제근거로 사용하지 않음

복원문제·후기 기반 정보는 공식자료와 동일한 수준으로 취급하지 않는다.

### 2. 공개자료의 한계

- 공개된 과거 기출/복원 자료는 전체 시험을 완전하게 대표한다고 단정할 수 없다.
- 특정 회차/후기에 등장했다는 이유만으로 `항상 출제`, `필수 Hint`, `고정 Plan 형태`로 일반화하지 않는다.
- 출제경향과 Oracle 기능의 존재 여부를 구분한다.

### 3. 실기 문제 형식에 대한 운영 가정

프로젝트에서 확인·정리한 문제 형식은 다음 세 축으로 관리한다.

1. **AS-IS Only 진단형**: AS-IS SQL/Plan을 보고 문제를 진단하고 개선안을 작성
2. **목표 Plan 역설계형**: 목표 TO-BE Plan 또는 일부 목표를 보고 SQL/Hint를 구성
3. **부분 TO-BE 혼합형**: 일부 Plan/Hint만 주고 나머지를 추론

중요: `언제나 TO-BE가 제공된다` 또는 `언제나 제공되지 않는다`고 가정하지 않는다.

기존 v1의 `AS-IS Only 최근 사례 많음 = 신뢰도 A` 표현은 공식근거와 복원자료 근거가 혼재할 수 있으므로, **공식근거가 별도 확인되지 않는 한 B 이하로 보수적으로 취급**한다.

### 4. 실기 직접 핵심 경향

현재 프로젝트 소스에서 실기 직접성이 높은 축은 다음과 같다.

- Cardinality / Selectivity / Starts / A-Rows
- Predicate 가공, 암묵변환, 날짜 범위 재작성
- Index Access 및 복합인덱스 설계
- NL / Hash / Merge 및 Join Order
- Semi / Anti / Outer / 1:N 결과집합 의미
- Scalar Subquery / Unnest / OR Expansion 등 핵심 Transformation
- DISTINCT / GROUP BY / Top-N / Sort
- Partition Pruning
- Full / Partial Partition-Wise Join
- Parallel Execution / PX Distribution
- DML / Batch / Partition DDL / 대량 UPDATE
- 개선 SQL의 결과집합 동일성

각 세부 중요도는 **통합패턴맵 최신 버전의 S/A 등급**을 따른다.

### 5. 통합패턴맵 확장영역의 해석

통합패턴맵 v2.3에는 다음 영역도 포함되어 있다.

- Parse / Execute / Fetch / Database Call
- SQL Trace / Response Time
- Lock / Transaction / Concurrency
- Performance Troubleshooting
- Optimizer Statistics 세부
- Plan Stability / Adaptive / 도구 영역
- SQLP 공식범위 문법 Safety Net

이 항목들이 패턴맵에 존재한다는 사실과 **최근 실기에서 동일한 깊이로 빈번하게 출제된다는 주장**은 동일하지 않다.

따라서:
- 통합패턴맵에서 **S/A**인 항목은 2회독 실전 대비 범위로 다룬다.
- **B/C/F**는 보조 Coverage/안전망으로 유지한다.
- 출제 빈도에 대한 별도 근거가 없으면 `최근 중요 출제경향`으로 과장하지 않는다.

### 6. 근거 부족으로 단정하지 않는 주장

다음은 단정하지 않는다.

- 언제나 TO-BE Plan이 제공된다.
- 특정 Hint가 항상 등장한다.
- TABLE ACCESS FULL이면 무조건 병목이다.
- PX SEND가 보이면 무조건 병목이다.
- Index가 존재하면 Index Scan이 항상 우월하다.
- 작은 테이블은 항상 Broadcast가 정답이다.
- Hash Join은 항상 작은 쪽이 특정 자식 위치에 있어야 한다.

실제 판단은 처리량, 선택도, Starts/A-Rows, 파티션/분배 구조, 결과집합 의미를 함께 본다.

### 7. 시험 답안 작성 원칙

기본 답안 사고 흐름은 다음으로 통일한다.

1. **결과집합/관계 확인**
   - 출력 컬럼
   - PK/FK/UK
   - 일반/Semi/Anti/Outer 관계
2. **건수 흐름 계산**
   - 필터 결과
   - Join 증폭/축소
   - Starts/A-Rows
   - GROUP BY/DISTINCT 결과
3. **AS-IS 병목 특정**
   - 단순 Operation명이 아니라 불필요 처리량의 직접 원인을 설명
4. **개선안 작성**
   - SQL / Hint / Index / DDL 중 필요한 수단 선택
5. **결과집합 동일성 검증**
6. **TO-BE Plan 핵심 흐름 검증**

### 8. Hint 사용 원칙

- Hint는 정답을 과도하게 고정하는 수단이 아니라 필요한 계획 의도를 전달하는 수단으로 사용한다.
- 공식 지원되는 Hint를 우선한다.
- `QB_NAME`, `LEADING`, Join Method, Access Path, `PQ_DISTRIBUTE` 등의 대상과 역할을 정확히 설명할 수 있어야 한다.
- 비공식/버전 의존성이 의심되는 Hint는 시험 기본답안의 필수 요소로 두지 않는다.

### 9. Oracle 버전 범용성

- 프로젝트 소스만으로 SQLP가 특정 Oracle 버전을 고정한다고 단정하지 않는다.
- 가능한 경우 버전 공통 원리를 우선한다.
- `FETCH FIRST` 같은 12c+ 문법을 사용할 경우 ROWNUM/ROW_NUMBER 기반 원리도 함께 이해한다.
- 기능의 존재 여부와 시험에서 해당 버전 세부동작을 요구한다는 주장을 구분한다.

### 🧭 1. 테이블 조인 순서(Join Order) 결정 5대 패턴 바이블

SQL에서 등장하는 모든 조인 구조는 아래 5대 패턴 중 하나로 완벽히 귀결됩니다.

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│  [패턴 1] 스타형 (중심 테이블 1개 + 날개 부모 테이블들) ── 가장 흔한 실무/시험 패턴   │
│  [패턴 2] 체인형 (부모 ──> 자식 ──> 손자 직렬 연결)                            │
│  [패턴 3] 마스터-디테일 집계형 (1:N 대량 거래 집계)                           │
│  [패턴 4] Top-N 페이징형 (ORDER BY + ROWNUM)                                 │
│  [패턴 5] 특수 조인형 (Outer / Semi / Anti)                                  │
└──────────────────────────────────────────────────────────────────────────────┘
```

---

##### 🏛️ [패턴 1] 스타형 (중심 테이블 + 날개 부모들) ── [출제율 50%]

중심 테이블(주문/거래/계약/배송)을 가운데 두고, 부모 테이블(고객/상품/센터/부서)들이 날개처럼 둘러싸고 있는 형태.

```text
  [부모 A : 종목/센터/상품] (20건)       [부모 B : 고객/부서] (5,000건)
            │                                    │
            │ (1:N)                              │ (1:N)
            ▼                                    ▼
       ┌──────────────────────────────────────────────┐
       │         [중심 테이블 : 주문/거래/배송]          │
       └──────────────────────────────────────────────┘
```

- **🎯 조인 순서 결정 공식:**
  **`[가장 깐깐한 부모 A (20건)]` ➡️ `[중심 테이블]` ➡️ `[나머지 부모 B]`**
- **동작 원리:**
  1. 단독 조건 건수가 가장 작은 **가장 좁은 입구(`부모 A`, 20건)**가 1등(Driving)!
  2. 부모 A의 조인 키를 들고 **`중심 테이블`**로 진입하여 데이터를 팍 줄임 (80,000건 -> 200건)!
  3. 줄어든 200건만 들고 반대편 **`부모 B`**의 PK를 200번만 콕콕 확인 (`Starts=200`).
- **표준 힌트:** `/*+ LEADING(부모A 중심테이블 부모B) USE_NL(중심테이블) USE_NL(부모B) */`

---

##### ⛓️ [패턴 2] 체인형 (직렬 연결: 부모 ➡️ 자식 ➡️ 손자) ── [출제율 20%]

테이블들이 1열로 줄줄이 연결된 구조. (예: `고객 ➡️ 주문 ➡️ 주문상세 ➡️ 배송`)

```text
[고객 (부모)] ──(1:N)──> [주문 (자식)] ──(1:N)──> [주문상세 (손자)] ──(1:1)──> [배송]
```

- **🎯 조인 순서 결정 공식:**
  > **"체인 상에서 '가장 강력한 필터(최소 건수)'가 걸려 있는 노드에서 출발하여 양옆으로 전파한다!"**
- **Case A (고객 쪽에 '특정 VIP 1명' 조건이 걸린 경우):**
  - 순서: `고객(1명)` ➡️ `주문` ➡️ `주문상세` ➡️ `배송` (Top-Down)
- **Case B (주문상세 쪽에 '특정 이벤트 상품 1개' 조건이 걸린 경우):**
  - 순서: `주문상세(10건)` ➡️ `주문` ➡️ `고객` ➡️ `배송` (Bottom-Up)

---

##### 📊 [패턴 3] 마스터-디테일 집계형 (1:N 대량 거래 집계) ── [출제율 15%]

마스터(고객 5,000명)와 대량 거래(거래 150만 건)를 조인하여 `SUM/COUNT` 집계하는 경우.

- **🎯 조인 순서 및 방식 공식:**
  > **"조인 대상 건수가 수만~수십만 건 이상이면 NL 조인의 Random I/O는 무너진다. HASH JOIN 또는 선집계 뷰를 사용하라!"**
- **해법 1 (Hash Join):**
  - 작은 테이블을 Build Input(해시 맵), 대량 테이블을 Probe Input으로 결합.
  - `/*+ LEADING(고객 거래) USE_HASH(거래) */`
- **해법 2 (선집계 인라인 뷰):**
  - 거래 테이블을 인라인 뷰에서 `GROUP BY`로 먼저 축약한 뒤 고객과 조인!

---

##### 🏎️ [패턴 4] Top-N 페이징형 (`ORDER BY + ROWNUM <= N`) ── [출제율 10%]

화면에서 가장 최근 데이터 10~20건만 빠르게 먼저 보여주어야 하는 부분범위 처리.

- **🎯 조인 순서 결정 공식:**
  > **"건수 크기와 무관하게, `ORDER BY` 정렬 인덱스를 가진 테이블이 무조건 1등(Driving)!"**
- 전체 주문이 500만 건이어도, 일자 인덱스를 거꾸로 읽으며 조건을 만족하는 10건을 채우면 **쿼리가 즉시 멈춤(COUNT STOPKEY)**!
- `/*+ LEADING(정렬인덱스보유테이블 타테이블) USE_NL(타테이블) */`

---

##### 🛡️ [패턴 5] 특수 조인형 (Outer / Semi / Anti) ── [출제율 5%]

1. **`LEFT OUTER JOIN`:**
   - 기준 테이블(보존되어야 하는 Left 테이블)이 **무조건 1등(Driving)**! (순서 뒤집기 불가)
2. **`EXISTS` (Semi-Join):**
   - 1:N 조인 증폭 및 `DISTINCT` 부하를 제거하고, 1건만 찾으면 즉시 멈추는 **Short-Circuit(조기 종료)** 실현!
   - `/*+ LEADING(메인 서브Q) USE_NL(서브Q) */` 또는 `/*+ UNNEST NL_SJ */`

### 📐 2. 결합 인덱스 설계의 황금 공식

인덱스를 설계할 때는 아래 **4단 서랍 공식**을 기계처럼 적용합니다.

**인덱스 컬럼 순서 = [ = 조건 컬럼들 ] + [ 조인 연결고리 키 ] + [ 범위(Between, <, >) 조건 ] + [ ORDER BY 정렬 컬럼 전수 ]**

##### 💡 인덱스 설계 핵심 원리 2가지
1. **등치(`=`) 조건 컬럼들의 순서 불변성:**
   - `=` 조건 컬럼들끼리는 인덱스 내에서 순서가 앞뒤로 바뀌어도 **스캔 범위와 I/O가 100% 동일함!**
   - 예: `(CENTER_CD, SEND_DT, DELIV_STAT, ...)` == `(CENTER_CD, DELIV_STAT, SEND_DT, ...)` (둘 다 만점)
2. **정렬 생략(Stopkey)을 위한 완전성:**
   - `ORDER BY 일자 DESC, 시간 DESC`에서 `시간` 컬럼이 인덱스에서 누락되면, 동일 일자 내 시간 정렬이 깨지므로 **오라클은 `SORT` 연산을 강제로 돌려버림!** (반드시 정렬 컬럼 몽땅 포함할 것)

### 📊 3. Starts vs A-Rows 판독 및 조인 메소드(NL vs HASH) 선택 기준

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  🔹 선행 집합이 [수 건 ~ 수천 건 이하 (소량)]  ➡️  무조건 NL JOIN (USE_NL)     │
│  🔹 선행 집합이 [수만 건 ~ 수십만 건 이상 (대량)] ➡️  무조건 HASH JOIN (USE_HASH)  │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **NL Join (Single Block Random I/O):**
  - 소량 건수(5건, 100건)에 대해 후행 테이블 인덱스를 몇 번만 콕콕 찍을 때 최적 (메모리 사용 없음, 첫 행 즉시 출력).
- **Hash Join (Multi-Block Sequential I/O + PGA):**
  - 대량 건수(50만 건) 조인 시 Random Access 부하를 없애고 메모리 해시 맵으로 고속 매칭.
- **Starts의 비밀:**
  - 상위 노드의 `A-Rows`(출력 건수)가 하위/내부 노드의 `Starts`(루프 반복 횟수)가 됨.
  - 시험 답안 병목 서술 시: *"선행 테이블 A-Rows N건으로 인해 후행 테이블 탐색이 N회 반복(Starts=N)되어 M건의 Random Access I/O 병목이 발생함"*으로 서술.

### 🛡️ 6. 서브쿼리 Unnesting & 뷰 머징(`NO_MERGE`) 완벽 바이블 (2026-08-17 보강)

##### (1) 서브쿼리 제어 3대 힌트 세트 공식

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 1. 서브쿼리를 조인(Semi-Join)으로 풀어서 처리할 때:                                         │
│    👉 /*+ UNNEST NL_SJ */   또는   /*+ UNNEST HASH_SJ */                               │
│                                                                                        │
│ 2. 서브쿼리를 절대 풀지 않고 메인 쿼리 뒤에서 FILTER로 남길 때:                              │
│    👉 /*+ NO_UNNEST */                                                                 │
│                                                                                        │
│ 3. 조인이 많은 쿼리에서 서브쿼리 FILTER를 조인 중간에 가장 먼저 적용하고 싶을 때:             │
│    👉 /*+ NO_UNNEST PUSH_SUBQ */                                                      │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

##### (2) 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN` 1회 집계 변환 공식

1. **스칼라의 본질은 `LEFT OUTER JOIN`:**
   - 상대 테이블 매칭 데이터가 없으면 `NULL`을 반환하는 특성이 있으므로, 조인 변환 시 반드시 **`LEFT OUTER JOIN`**을 사용하여 메인 집합의 유실을 방지한다.
2. **동일 테이블 중복 스캔 제거 (`CASE WHEN` 1회 집계):**
   - 동일 테이블에 대해 정상금액(`SUM`)과 반품건수(`COUNT`)를 각각 스칼라로 쪼개지 말고, **단 1개의 인라인 뷰에서 `CASE WHEN`으로 동시에 집계**한다.
   - 금액 합계: `SUM(CASE WHEN 조건 THEN 금액 END)`
   - 건수 카운트: `COUNT(CASE WHEN 조건 THEN 1 END)`
3. **대량 결합은 `USE_HASH`:**
   - 메인 데이터가 수만 건 이상이고, 선집계된 인라인 뷰(`V`)에는 B-Tree 인덱스가 없으므로 **무조건 `USE_HASH(V)`**를 지정한다.

##### (3) [오라클 공식 규정] 뷰 머징(View Merging) 원천 불가 8대 제약사항

아래 항목이 인라인 뷰 내에 포함되어 있으면, 오라클은 힌트와 무관하게 **뷰 머징을 100% 포기하고 무조건 독립적인 `VIEW` 오퍼레이션으로 실행**합니다:

| 번호 | 제약 요소 | 상세 설명 및 예시 |
|:---:|---|---|
| **1** | **`ROWNUM` 의사컬럼** | `WHERE ROWNUM <= 10` 등 Top-N 페이징 처리가 들어간 뷰 |
| **2** | **집합 연산자 (Set Operators)** | `UNION`, `UNION ALL`, `INTERSECT`, `MINUS`가 사용된 뷰 |
| **3** | **계층형 쿼리 (Hierarchical Query)** | `START WITH`, `CONNECT BY` 절이 포함된 계층형 뷰 |
| **4** | **`GROUP BY` 없는 집계 함수** | `SELECT SUM(AMT), AVG(QTY) FROM ...` 처럼 전체 단 1행만 반환하는 스칼라 집계 뷰 |
| **5** | **분석/윈도우 함수 (Analytic Functions)** | `ROW_NUMBER()`, `RANK()`, `SUM() OVER (...)` 등이 포함된 뷰 |
| **6** | **`MODEL` 절** | 오라클 다차원 모델링 `MODEL` 구문이 사용된 뷰 |
| **7** | **시퀀스 및 비결정적 함수** | 뷰의 SELECT 목록에 `SEQ.NEXTVAL` 또는 비결정적(Non-deterministic) 함수 포함 시 |
| **8** | **XMLTable / Flashback 절** | `XMLTABLE(...)` 구문 또는 `AS OF TIMESTAMP/SCN` 과거 시점 조회가 포함된 뷰 |

##### (4) [튜너의 무기] 튜너가 직접 `/*+ NO_MERGE */`를 거는 5대 실무 목적

오라클이 머징을 시도할 수 있는 상황에서, 성능을 위해 튜너가 의도적으로 머징을 차단하는 핵심 케이스:

1. **[선집계 강제]** `GROUP BY`로 수천만 건을 수만 건으로 먼저 축소한 뒤 메인과 결합할 때 (Complex View Merging 방지).
2. **[선중복제거]** `DISTINCT`로 대량 집합의 중복을 먼저 깎아낸 뒤 조인할 때.
3. **[조인순서 통제]** 5~6개 복잡한 테이블 조인 시 인라인 뷰를 '독립 블록'으로 묶어 `LEADING` 순서를 통제할 때.
4. **[조인증폭 방지]** 1:N:M 관계에서 중간 카디널리티 폭발(데카르트곱)을 막고 싶을 때.
5. **[함수호출 지연]** 무거운 PL/SQL 사용자 정의 함수 호출을 최종 10건 필터링 뒤로 미루어 호출 횟수를 극소화할 때.

##### 📋 [문제 1] 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN` 1회 집계 + `USE_HASH`

* **상황:** 배송기사 15,000명(`TB_DRIVER`)에 대해 프로필(`TB_DRIVER_PROFILE`)과 1,500만 건 배송이력(`TB_DELIVERY_LOG`)의 완료금액(`SUM`)과 실패건수(`COUNT`)를 각각 스칼라로 조회하여 45,000회 I/O 폭발.

###### 💯 [만점 정답 SQL]
```sql
SELECT /*+ LEADING(D P V) USE_NL(P) USE_HASH(V)
           INDEX(D IX_DRIVER_01) INDEX(P PK_TB_DRIVER_PROFILE) */
       D.DRIVER_ID,
       D.DRIVER_NM,
       P.CAR_TYPE_CD,
       NVL(V.DONE_FEE_AMT, 0) AS DONE_FEE_AMT,
       NVL(V.FAIL_CNT, 0)     AS FAIL_CNT
  FROM TB_DRIVER D
  LEFT OUTER JOIN TB_DRIVER_PROFILE P 
    ON P.DRIVER_ID = D.DRIVER_ID
  LEFT OUTER JOIN (
       SELECT /*+ NO_MERGE INDEX(L IX_DELIV_01) */
              L.DRIVER_ID,
              SUM(CASE WHEN L.DELIV_STAT_CD = 'DONE' THEN L.DELIV_FEE ELSE 0 END) AS DONE_FEE_AMT,
              COUNT(CASE WHEN L.DELIV_STAT_CD = 'FAIL' THEN 1 END)                AS FAIL_CNT
         FROM TB_DELIVERY_LOG L
        WHERE L.DELIV_DT >= '20260101'
        GROUP BY L.DRIVER_ID
  ) V
    ON V.DRIVER_ID = D.DRIVER_ID
 WHERE D.AREA_CD = 'SEOUL'
   AND D.JOIN_DT >= '20260101';
```

> **대표 판단:** NL/Hash/Merge, Driving, Build/Probe
> **핵심 기준:** K13 드라이빙 · K14 도달 가능성 · K15 LEADING 인접성 · K16 USE_NL 대상 · K17 자릿수 비교법 · K18 손익분기 · K19 배치/온라인


### T03 · 답안 골격 ①②③

| | 확정할 것 |
|---|---|
| ① | 건수 축소 순서: `[조건] N건 → M건` 을 축소 효과가 큰 순으로 나열 |
| ② | 조인 순서: `T1 → T2 → T3 → T4` + **인접 쌍마다 조인 조건 1줄** (카티시안 방지) |
| ③ | 조인 방식: 바깥 건수 vs **손익분기 = 안쪽 테이블 블록수 ÷ 4** 비교 |

```
NL   비용 ≈ 바깥건수 × (인덱스높이 + 1)   ≈ ×4
HASH 비용 ≈ 안쪽 테이블 총 블록수 (1회)
→ 바깥건수 > 블록수÷4 이면 HASH+FULL, 아니면 NL+인덱스
```

> FULL은 `USE_HASH` 와 세트다. NL의 inner에 FULL을 걸면 바깥 건수만큼 풀스캔이 반복된다.

## T05 Scalar Subquery / Query Transformation

> **범위:** `Q01~Q08`, `Q13~Q15`, `R04`/`R12`/`R13`/`R15`
> **대표 판단:** 반복 Starts, Unnest, Push, Merge
> **핵심 기준:** K25 UNNEST 시 LEADING 구성 · K26 두 접근안 병기 · K27 NO_MERGE/PUSH_PRED · K28 PUSH_PRED 짝


### T05 · 답안 골격 ①②③

| | 확정할 것 |
|---|---|
| ① | 서브쿼리 필터의 **선택도**와 현재 **적용 시점** (조인 앞인가 뒤인가) |
| ② | 풀 것인가 말 것인가 → **LEADING 구성이 갈린다** |
| ③ | 스칼라라면: `LEFT OUTER JOIN` + `CASE WHEN` 1회 집계 + `USE_HASH(V)` |

```
안 푼다 → 서브Q에 /*+ NO_UNNEST PUSH_SUBQ */ , LEADING에서 서브Q 제외
푼다   → 서브Q에 /*+ UNNEST */ , LEADING 2순위에 서브Q + USE_NL + NL_SJ
인라인 뷰 → NO_UNNEST가 아니라 /*+ NO_MERGE */
```

> 동일 상관키가 반복 유입되면 `FILTER`의 서브쿼리 결과 캐싱이 작동해 NO_UNNEST 쪽이 유리할 수 있다.

### 📊 2. 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN 1회 집계` 변환 공식

##### 💡 3대 변환 원칙
1. **스칼라의 본질은 `LEFT OUTER JOIN`:**
   - 상대 테이블에 매칭 데이터가 없어도 메인 집합이 탈락하지 않도록 반드시 **`LEFT OUTER JOIN`**을 사용한다.
2. **`CASE WHEN` 1회 집계 (중복 스캔 100% 제거):**
   - 동일 테이블에 대해 정상금액(`SUM`)과 반품/실패건수(`COUNT`)를 각각 쪼개지 말고, **단 1개의 인라인 뷰에서 `CASE WHEN`으로 동시에 집계**한다.
   - **금액 합계:** `SUM(CASE WHEN 조건 THEN 금액컬럼 END)`
   - **건수 카운트:** `COUNT(CASE WHEN 조건 THEN 1 END)` 또는 `SUM(CASE WHEN 조건 THEN 1 ELSE 0 END)`
3. **대량 결합은 무조건 `USE_HASH`:**
   - `GROUP BY`가 완료된 인라인 뷰(`V`) 메모리 집합에는 **B-Tree 인덱스가 없으므로** 대량 조인 시 `USE_NL`을 쓰면 부하가 터진다. 무조건 **`USE_HASH(V)`**를 지정한다.

### 🏛️ 3. 뷰 머징(View Merging) & `NO_MERGE` 총망라 가이드

##### (1) [오라클 공식 규정] 뷰 머징 원천 불가 8대 제약사항 (Non-Mergeable Views)
아래 항목이 인라인 뷰 내에 포함되어 있으면, 힌트와 무관하게 **오라클이 알아서 머징을 포기하고 독립적인 `VIEW` 오퍼레이션으로 실행**합니다:

| 번호 | 제약 요소 | 상세 설명 및 예시 |
|:---:|---|---|
| **1** | **`ROWNUM` 의사컬럼** | `WHERE ROWNUM <= 10` 등 Top-N 페이징 처리가 들어간 뷰 |
| **2** | **집합 연산자 (Set Operators)** | `UNION`, `UNION ALL`, `INTERSECT`, `MINUS`가 사용된 뷰 |
| **3** | **계층형 쿼리 (Hierarchical Query)** | `START WITH`, `CONNECT BY` 절이 포함된 계층형 뷰 |
| **4** | **`GROUP BY` 없는 집계 함수** | `SELECT SUM(AMT), AVG(QTY) FROM ...` 처럼 전체 단 1행만 반환하는 스칼라 집계 뷰 |
| **5** | **분석/윈도우 함수 (Analytic Functions)** | `ROW_NUMBER()`, `RANK()`, `SUM() OVER (...)` 등이 포함된 뷰 |
| **6** | **`MODEL` 절** | 오라클 다차원 모델링 `MODEL` 구문이 사용된 뷰 |
| **7** | **시퀀스 및 비결정적 함수** | 뷰의 SELECT 목록에 `SEQ.NEXTVAL` 또는 비결정적 함수 포함 시 |
| **8** | **XMLTable / Flashback 절** | `XMLTABLE(...)` 구문 또는 `AS OF TIMESTAMP/SCN` 과거 시점 조회가 포함된 뷰 |

##### (2) [튜너의 무기] 튜너가 직접 `/*+ NO_MERGE */`를 거는 5대 실무 목적
1. **[선집계 강제]** `GROUP BY`로 수천만 건을 수만 건으로 먼저 축소한 뒤 메인과 결합할 때 (Complex View Merging 방지).
2. **[선중복제거]** `DISTINCT`로 대량 집합의 중복을 먼저 깎아낸 뒤 조인할 때.
3. **[조인순서 통제]** 5~6개 복잡한 테이블 조인 시 인라인 뷰를 '독립 블록'으로 묶어 `LEADING` 순서를 통제할 때.
4. **[조인증폭 방지]** 1:N:M 관계에서 중간 카디널리티 폭발(데카르트곱)을 막고 싶을 때.
5. **[함수호출 지연]** 무거운 PL/SQL 사용자 정의 함수 호출을 최종 10건 필터링 뒤로 미루어 호출 횟수를 극소화할 때.

##### 📋 [실전 문제 1] 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN 1회 집계` + `USE_HASH`

* **상황:** 배송기사 15,000명(`TB_DRIVER`)에 대해 프로필(`TB_DRIVER_PROFILE`)과 1,500만 건 배송이력(`TB_DELIVERY_LOG`)의 완료금액(`SUM`)과 실패건수(`COUNT`)를 각각 스칼라로 조회하여 45,000회 I/O 폭발.

###### 💯 [만점 정답 SQL]
```sql
SELECT /*+ LEADING(D P V) USE_NL(P) USE_HASH(V)
           INDEX(D IX_DRIVER_01) INDEX(P PK_TB_DRIVER_PROFILE) */
       D.DRIVER_ID,
       D.DRIVER_NM,
       P.CAR_TYPE_CD,
       NVL(V.DONE_FEE_AMT, 0) AS DONE_FEE_AMT,
       NVL(V.FAIL_CNT, 0)     AS FAIL_CNT
  FROM TB_DRIVER D
  LEFT OUTER JOIN TB_DRIVER_PROFILE P 
    ON P.DRIVER_ID = D.DRIVER_ID
  LEFT OUTER JOIN (
       SELECT /*+ NO_MERGE INDEX(L IX_DELIV_01) */
              L.DRIVER_ID,
              SUM(CASE WHEN L.DELIV_STAT_CD = 'DONE' THEN L.DELIV_FEE ELSE 0 END) AS DONE_FEE_AMT,
              COUNT(CASE WHEN L.DELIV_STAT_CD = 'FAIL' THEN 1 END)                AS FAIL_CNT
         FROM TB_DELIVERY_LOG L
        WHERE L.DELIV_DT >= '20260101'
        GROUP BY L.DRIVER_ID
  ) V
    ON V.DRIVER_ID = D.DRIVER_ID
 WHERE D.AREA_CD = 'SEOUL'
   AND D.JOIN_DT >= '20260101';
```

##### 📋 [실전 문제 2] 서브쿼리 조기 필터링 (`PUSH_SUBQ` vs `UNNEST NL_SJ`)

* **상황:** 당일 예약자 10,000건(`TB_RESERV`)에 대해 진료과(`TB_DEPT`)와 의사(`TB_DOCTOR`)를 20,000회 헛조인한 뒤, 맨 마지막에 당일 중증 응급로그(`TB_EMERGENCY_LOG`, 단 20건)로 거르는 비효율 해소.

###### 💯 [방식 1: PUSH_SUBQ 정답 (서브쿼리 안에 힌트 추가)]

### 🛡️ 1. 선택적 검색조건 4대 패턴과 최적 해법

| 패턴 유형 | AS-IS 구현 형태 | 문제점 | 최적 TO-BE 해법 |
|---|---|---|---|
| **1. 단일 컬럼 NVL** | `WHERE COL = NVL(:b, COL)` | NULL 입력 시 `COL IS NOT NULL`로 변환되어 인덱스 스캔 불가 또는 FTS 발생 | `UNION ALL` 분기 (`:b IS NOT NULL` vs `:b IS NULL`) 또는 `OR Expansion` |
| **2. 다중 컬럼 NVL** | `WHERE CUST_ID = NVL(:c, CUST_ID) AND DEPT_NO = NVL(:d, DEPT_NO)` | 하나의 실행계획으로 다양한 입력 패턴(고객만, 부서만, 둘다)을 만족할 수 없어 비효율 발생 | 입력 조합의 선택도/빈도에 따라 **우선순위 기반 `UNION ALL` 배타적 분기** |
| **3. 컬럼 간 OR 조건** | `WHERE (A_CD = :a OR B_CD = :b)` | 단일 인덱스로 양쪽 컬럼을 동시에 Range Scan 불가 ➜ FTS 유도됨 | **`UNION ALL` + `LNNVL` 함수**를 통한 중복 제거 분기 |
| **4. IN-List + Top-N** | `WHERE STAT_CD IN ('A', 'B') ORDER BY REG_DT DESC (ROWNUM <= 10)` | 각 인-리스트 브랜치 내부에서 정렬되므로 최종 결과 정렬 생략 불가 (`SORT ORDER BY`) | **각 조건별 `ROWNUM <= 10` 인라인 뷰 사전 추출** 후 최종 결합 Top-10 |

### 📊 2. `LNNVL` 함수를 활용한 상호배타적 `UNION ALL` 분기 공식

##### 💡 `LNNVL(condition)` 함수의 물리적 동작 원리
* `LNNVL(조건)`은 해당 조건이 **`FALSE`이거나 `UNKNOWN(NULL)`일 때만 `TRUE`**를 반환합니다.
* 즉, **"앞선 브랜치에서 이미 처리된 데이터를 후속 브랜치에서 완벽히 제외"**하여 `UNION ALL` 수행 시 `UNION`의 정렬/중복제거 부하 없이 동일한 결과를 100% 보장합니다.

```sql
-- [표준 모범 패턴] 컬럼별 OR 조건을 상호배타적 UNION ALL로 변환
SELECT /*+ INDEX(A IX_TB_DOC_01) */
       DOC_NO, REG_DT, CUST_ID, DEPT_CD
  FROM TB_DOC A
 WHERE CUST_ID = :CUST_ID  -- 1. 고객번호 인덱스 활용 (우선 추출)
UNION ALL
SELECT /*+ INDEX(A IX_TB_DOC_02) */
       DOC_NO, REG_DT, CUST_ID, DEPT_CD
  FROM TB_DOC A
 WHERE DEPT_CD = :DEPT_CD
   AND LNNVL(CUST_ID = :CUST_ID); -- 2. 앞선 1번 브랜치에서 조회된 고객 데이터 완벽 제외!
```

### ⚡ 3. IN-List + Top-N 쿼리 정렬 부하 제거 (브랜치 사전 Stopkey)

##### 💡 왜 IN-List는 `SORT ORDER BY`를 생략할 수 없는가?
* `INLIST ITERATOR`는 `STAT_CD = 'A'`를 인덱스로 역순 정렬 스캔하고, 이어서 `STAT_CD = 'B'`를 인덱스로 역순 정렬 스캔합니다.
* 하지만 'A' 그룹 내부와 'B' 그룹 내부는 각각 정렬되어 있어도, **두 그룹을 합친 전체 데이터는 `REG_DT` 순서로 정렬되어 있지 않기 때문에** 최종 `SORT ORDER BY` 연산이 불가피하게 발생합니다.

##### 🏆 [표준 정답] 브랜치별 사전 Top-N 추출 공식
```sql
SELECT *
  FROM (
        SELECT /*+ INDEX_DESC(A IX_TB_ORD_01) */
               ORD_NO, ORD_DT, STAT_CD, ORD_AMT
          FROM TB_ORD A
         WHERE STAT_CD = 'A'
           AND ROWNUM <= 10 -- 브랜치 1: 최대 10건만 읽고 즉시 Stop!
        UNION ALL
        SELECT /*+ INDEX_DESC(A IX_TB_ORD_01) */
               ORD_NO, ORD_DT, STAT_CD, ORD_AMT
          FROM TB_ORD A
         WHERE STAT_CD = 'B'
           AND ROWNUM <= 10 -- 브랜치 2: 최대 10건만 읽고 즉시 Stop!
       )
 ORDER BY ORD_DT DESC
 FETCH FIRST 10 ROWS ONLY; -- (또는 WHERE ROWNUM <= 10)
```
* **성능 효과:** 수백만 건 전체를 정렬하는 대참사를 막고, 단 20건만 읽어서 10건을 추출하므로 I/O가 99.9% 절감됩니다.

### 🛡️ 1. 다측(N) 선집계 인라인 뷰 변환 3대 원칙

##### 💡 1:N 조인 후 GROUP BY vs 사전 선집계 비교
* **AS-IS (조인 후 집계):** 1(마스터 10만) $\times$ N(상세 1,000만) $\rightarrow$ **1,000만 건 조인 증폭** $\rightarrow$ `HASH GROUP BY` (1,000만 건 정렬/해시 부하)
* **TO-BE (사전 선집계 후 조인):** N(상세 1,000만) $\rightarrow$ **사전 `GROUP BY` (10만 건 축소)** $\rightarrow$ 마스터 10만 건과 1:1 `USE_HASH` 결합 (중간 집합 99% 급감!)

```sql
-- [표준 모범 패턴] 다측 선집계 인라인 뷰 + USE_HASH
SELECT /*+ LEADING(C V) USE_HASH(V) */
       C.CUST_ID,
       C.CUST_NM,
       NVL(V.ORD_CNT, 0)   AS ORD_CNT,
       NVL(V.TOTAL_AMT, 0) AS TOTAL_AMT
  FROM TB_CUST C
  LEFT OUTER JOIN (
       SELECT /*+ NO_MERGE */
              CUST_ID,
              COUNT(ORD_NO) AS ORD_CNT,
              SUM(ORD_AMT)  AS TOTAL_AMT
         FROM TB_ORD
        WHERE ORD_DT BETWEEN '20260101' AND '20260630'
        GROUP BY CUST_ID
       ) V
    ON C.CUST_ID = V.CUST_ID
 WHERE C.GRADE_CD = 'VIP';
```

### ⚡ 2. 그룹별 최신 1건 (Top-1) 고속 추출 2대 해법

##### 💡 해법 1: `PUSH_PRED` + `USE_NL` 상관 인라인 뷰 기법
* **적용 조건:** Outer(사원/고객) 건수가 소량(수천 건 이하)이고, Inner에 `(EMP_ID, APPR_DT DESC)` 결합 인덱스가 있을 때
* **동작 원리:** 인라인 뷰 내부로 Outer의 `EMP_ID` 조건이 침투(`PUSH_PRED`)하여, 사원당 최신 1건만 인덱스로 읽고 Stopkey 종료.

```sql
-- [인덱스] IX_TB_APPR_01: (EMP_ID, APPR_DT DESC, APPR_NO)
SELECT /*+ LEADING(E V) USE_NL(V) */
       E.EMP_ID,
       E.EMP_NM,
       V.APPR_NO,
       V.APPR_DT,
       V.APPR_AMT
  FROM TB_EMP E,
       LATERAL ( -- 또는 PUSH_PRED 적용 상관 서브쿼리
       SELECT /*+ NO_MERGE PUSH_PRED */
              A.APPR_NO, A.APPR_DT, A.APPR_AMT
         FROM TB_APPR A
        WHERE A.EMP_ID = E.EMP_ID
        ORDER BY A.APPR_DT DESC
        FETCH FIRST 1 ROWS ONLY
       ) V
 WHERE E.DEPT_CD = 'D01';
```

##### 💡 해법 2: `ROW_NUMBER` + `WINDOW NOSORT` 인덱스 활용 기법
* **적용 조건:** 전체 사원에 대해 일괄 배치 추출할 때
* **인덱스 설계:** `(EMP_ID, APPR_DT DESC)`로 인덱스를 생성하면 `ROW_NUMBER() OVER (PARTITION BY EMP_ID ORDER BY APPR_DT DESC)` 수행 시 정렬 연산이 100% 생략(`WINDOW NOSORT`)됩니다.

### 🛡️ 1. Static Pruning vs Dynamic Pruning 비교

| 구분 | Static Partition Pruning | Dynamic Partition Pruning |
|---|---|---|
| **결정 시점** | SQL 컴파일/하드파싱 시점 | SQL 런타임(실행) 시점 |
| **조건 형태** | 상수 리터럴 (`ORD_DT = '20260801'`) | 바인드 변수, 서브쿼리, 조인 연결고리 |
| **실행계획 Pstart / Pstop** | `1` ~ `1` (또는 특정 파티션 번호) | `KEY` ~ `KEY` (또는 `KEY(INLIST)`) |
| **핵심 주의점** | 파티션 키 컬럼 가공(`SUBSTR`, 형변환) 금지 | **선행 테이블로부터 값을 건네받는 `Nested Loops 조인(USE_NL)`**에서만 작동 |

### ⚡ 2. 파티션 키 없는 Top-N 조회 시 로컬 vs 글로벌 인덱스

##### 💡 왜 파티션 키 없는 조건의 Top-N에 로컬 인덱스는 치명적인가?
* 로컬 인덱스는 **각 파티션 내부에서만 정렬**되어 있습니다.
* 따라서 `WHERE ROWNUM <= 10 ORDER BY REG_DT DESC`를 실행할 때, 오라클은 12개 또는 365개 **모든 파티션의 로컬 인덱스를 전부 뒤져서 데이터를 모은 뒤 최종 `SORT ORDER BY STOPKEY`**를 수행해야 하므로 파티션 개수만큼 I/O가 폭발합니다.

##### 🏆 [물리적 해결책] 글로벌 비파티션 인덱스 (Global Non-Partitioned Index)
* **인덱스 생성:** `CREATE INDEX IX_TB_ORD_GLOBAL ON TB_ORD(ORD_STAT, REG_DT DESC);`
* **동작 원리:** 테이블이 수백 개 파티션으로 쪼개져 있어도, 인덱스는 전체 테이블에 대해 단일 B-Tree로 완벽히 정렬되어 있으므로 **단 10건만 읽고 즉시 `COUNT STOPKEY`로 종료 (정렬 연산 100% 제거)!**

### 🛡️ 1. `PQ_DISTRIBUTE` 3대 킬러 공식 요약표

| 조인 상황 및 물리적 구조 | 최적 분배 전략 | 표준 힌트 구문 | 물리적 효과 및 전송량 |
|---|---|---|---|
| **1. 대량 ↔ 소량 (수만 건 이하)** | **BROADCAST** | `/*+ LEADING(A B) USE_HASH(B) PQ_DISTRIBUTE(B, BROADCAST, NONE) */` | 소량(A)을 모든 슬레이브에 복제 전송, B는 로컬 스캔 |
| **2. 대량 ↔ 대량 (수백만 건 이상)** | **HASH HASH** | `/*+ LEADING(A B) USE_HASH(B) PQ_DISTRIBUTE(B, HASH, HASH) */` | 양쪽 모두 조인 키 기준 1/N 균등 분할 전송, 메모리 절감 |
| **3. 한쪽만 조인키 파티션 테이블** | **Partial PWJ** | `/*+ LEADING(A B) USE_HASH(B) PQ_DISTRIBUTE(B, PARTITION, NONE) */` | A를 B의 파티션 맵으로 1회 분배, B는 로컬 스캔 |
| **4. 양쪽 모두 조인키 동등 파티션** | **Full PWJ** | `/*+ LEADING(A B) USE_HASH(B) PQ_DISTRIBUTE(B, NONE, NONE) */` | **통신량 0건!** 파티션 쌍끼리 1:1 로컬 조인 |

### ⚡ 2. 1개 Slave Set vs 2개 Slave Set 판독법

* **1개 Slave Set (`Q1,00`만 존재, 총 DOP개 프로세스):**
  * `Full PWJ (NONE, NONE)`, `Partial PWJ (PARTITION, NONE)`, `BROADCAST (BROADCAST, NONE)`의 Inner 단계처럼 **생산자-소비자 분리 없이 한 세트가 순차 처리**할 때.
* **2개 Slave Set (`Q1,00`, `Q1,01` 동시 가동, 총 2 × DOP개 프로세스):**
  * `HASH HASH (HASH, HASH)` 분배처럼 양쪽 데이터를 서로 다른 슬레이브가 동시에 읽어 해시 교차 전송할 때.

##### 📦 2. [T10] DML / Batch / DDL 핵심 개념 및 단계별 가이드

###### 📌 [초급] 대량 DELETE 한계 & CTAS 5단계 표준 절차
1. **대량 DELETE의 3대 물리적 병목:**
   - **Undo/Redo 폭증:** 지워지는 모든 행의 전후 데이터를 Undo 세그먼트와 Redo 로그에 기록하므로 I/O 및 공간 고갈 발생.
   - **인덱스 유지 비용:** 테이블의 행 삭제 시 해당 테이블에 걸린 모든 인덱스 Leaf 노드에서 건건이 삭제 마킹(Delete Flag)을 수행하여 엄청난 Random I/O 유발.
   - **HWM(High Water Mark) 유지:** DELETE는 공간을 반환하지 않으므로 테이블 세그먼트의 HWM이 그대로 유지되어 이후 Full Scan 성능 영구 저하.
2. **CTAS 5단계 표준 DDL 절차:**
   - **Step 1:** 보존할 데이터(예: 5%)만 추출하여 NOLOGGING + PARALLEL로 임시 테이블 생성 (CREATE TABLE ... AS SELECT ...)
   - **Step 2:** 신규 임시 테이블에 PK 제약조건 및 필수 인덱스 일괄 생성 (NOLOGGING + PARALLEL)
   - **Step 3:** 원본 테이블 백업 또는 즉시 삭제 (DROP TABLE TB_ORIGIN PURGE;)
   - **Step 4:** 임시 테이블을 원본 테이블명으로 변경 (RENAME TB_TEMP TO TB_ORIGIN;)
   - **Step 5:** 테이블 및 인덱스를 LOGGING 및 NOPARALLEL로 정상화 복구

###### 📌 [중급] EXCHANGE PARTITION & 스테이징 사전 인덱스
- **원리:** 데이터 복사 없이 딕셔너리의 세그먼트 메타데이터 포인터만 맞바꾸는 최고속 교체 기법.
- **핵심 급소 (사전 인덱스):** INCLUDING INDEXES 옵션 사용 시, 파티션 테이블에 로컬 인덱스가 존재한다면 **임시(스테이징) 테이블에도 동일한 컬럼 순서의 일반 인덱스가 사전에 생성되어 있어야만** 파티션 교체 후 로컬 인덱스가 UNUSABLE로 깨지지 않고 유지됨.

###### 📌 [고급] 대량 INSERT(UNUSABLE) & 대량 UPDATE(MERGE)
- **Direct-Path INSERT:** 인덱스를 UNUSABLE 처리 ➡️ INSERT /*+ APPEND PARALLEL */ ➡️ ALTER INDEX ... REBUILD PARALLEL 순으로 대량 적재.
- **대량 UPDATE:** 상관 서브쿼리 UPDATE 80만 회 반복 ➡️ MERGE INTO ... USING (선집계 뷰) ... ON (...) + USE_HASH로 단 1회 조인 갱신.

##### ⚡ 3. [T11] Runtime / Trace / DB Call 핵심 개념 및 단계별 가이드

###### 📌 [초급] Parse/Execute/Fetch & Array Processing
1. **SQL 수행 3단계:**
   - **Parse:** 문법 검사, 의미 분석, 권한 확인, Shared Pool 캐싱 확인 및 최적화 실행계획 생성.
   - **Execute:** 커서 오픈, 바인드 변수 바인딩, 데이터 추출 준비 (SELECT는 실행계획 셋업, DML은 실제 데이터 변경).
   - **Fetch:** SELECT 쿼리에서 실제 결과 로우(Row)를 서버 버퍼캐시에서 읽어 애플리케이션으로 전송.
2. **Fetch Count 산출 공식:**
   \text{Fetch Count} = \text{TRUNC}\left(\frac{\text{총 반환 행수}}{\text{Array Size}}\right) + 1
   *(※ 정확히 나누어떨어져도 마지막에 더 이상 읽을 데이터가 없음을 확인하는 EOF Fetch Call 1회가 반드시 추가됨)*
3. **Array Size 설정의 Trade-off:**
   - Array Size를 키우면 Network Round-Trip(DB Call) 및 Block Pinning I/O가 대폭 감소하지만, 클라이언트/서버 메모리(PGA) 사용량이 증가하므로 통상 100~500 수준이 최적.

###### 📌 [중급] TKPROF 지표 분석 & Row-by-Row ➡️ Set MERGE
- **Consistent Gets (query) vs DB Block Gets (current):**
  - query: SELECT 조회 시 CR 블록을 읽을 때 발생.
  - current: INSERT/UPDATE/DELETE 시 최신 블록을 직접 읽고 변경할 때 발생.
- **Set Processing 전환:**
  - 루프 내 건건이 SELECT ➡️ UPDATE / INSERT 분기 ➡️ 단일 MERGE INTO ... USING (선집계 뷰) ON (...) WHEN MATCHED ... WHEN NOT MATCHED ... 구문으로 통합하여 Call 횟수를 수만 회에서 **단 1회**로 축소.

##### 🔒 4. [T12] Lock / Transaction / Concurrency 핵심 개념 및 단계별 가이드

###### 📌 [초급] TX Row Lock vs TM Table Lock
- **TX Lock (Row-Level):** 동일한 행을 서로 다른 두 세션이 동시에 UPDATE/DELETE하려 할 때 발생 (배타적 락).
- **TM Lock (Table-Level):** 자식 테이블의 **외래키(FK) 컬럼에 인덱스가 없는 상태**에서 부모 테이블의 행을 삭제/수정할 때, 자식 테이블 전체에 Share Lock (TM)이 걸려 자식 테이블의 모든 DML이 전면 블로킹됨.

###### 📌 [중급] Blocker 추적 & Commit 주기 및 SELECT FOR UPDATE
- **Blocker 식별:** 대기 중인 Waiter 세션만 볼 것이 아니라, 락을 쥐고 있는 Blocker 세션의 트랜잭션 시작 시점과 SQL을 찾아야 함.
- **Commit 주기:** 루프 건건이 Commit은 Redo Log Sync I/O 폭증과 Snapshot Too Old (ORA-01555)를 유발하고, 너무 늦은 Commit은 락 유지시간을 증가시키므로 적정 배치 단위(예: 5,000~10,000건) 분할 커밋이 원칙.
- **동시성 제어:** SELECT ... FOR UPDATE NOWAIT 또는 SKIP LOCKED를 활용한 큐잉 시스템 튜닝.

### 필수 문법 템플릿 (백지 작성 대상)

##### 📦 [T10] DML / Batch / DDL (대용량 데이터 처리)

###### 1. CTAS 5단계 표준 절차 (대량 삭제/복제)
대량의 데이터를 지우거나 복제할 때 Undo/Redo를 제거하고 가장 빠르게 처리하는 정석 절차.

```sql
-- [Step 1] 데이터 복제 (NOLOGGING + PARALLEL 4 필수)
CREATE TABLE 임시테이블 NOLOGGING PARALLEL 4
AS 
SELECT /*+ FULL(A) PARALLEL(A 4) */ * 
FROM   원본테이블 A 
WHERE  조건;

-- [Step 2] PK 및 일반 인덱스 후속 일괄 빌드 (데이터 적재 후 생성해야 Index Split 방지)
CREATE UNIQUE INDEX PK_임시_명칭 ON 임시테이블 (PK컬럼1, PK컬럼2) NOLOGGING PARALLEL 4;
ALTER TABLE 임시테이블 ADD CONSTRAINT PK_임시_명칭 PRIMARY KEY (PK컬럼1, PK컬럼2) USING INDEX PK_임시_명칭;

CREATE INDEX IX_임시_명칭 ON 임시테이블 (일반컬럼1, 일반컬럼2) NOLOGGING PARALLEL 4;

-- [Step 3] 원본 파괴 (공간 즉시 반환을 위해 PURGE 필수)
DROP TABLE 원본테이블 PURGE;

-- [Step 4] RENAME 원복 (테이블과 인덱스 모두 이름 원복)
RENAME 임시테이블 TO 원본테이블;
ALTER INDEX PK_임시_명칭 RENAME TO PK_원본_명칭;
ALTER INDEX IX_임시_명칭 RENAME TO IX_원본_명칭;

-- [Step 5] 서비스 정상화 릴리즈 (가장 중요! 로깅 복구 및 병렬도 해제)
ALTER TABLE 원본테이블 LOGGING NOPARALLEL;
ALTER INDEX PK_원본_명칭 LOGGING NOPARALLEL;
ALTER INDEX IX_원본_명칭 LOGGING NOPARALLEL;
```

###### 2. 파티션 교체 (EXCHANGE PARTITION) 및 사전 인덱스 매핑
파티션 교체 시 로컬 인덱스가 `UNUSABLE`로 깨지는 것을 막기 위한 문법.

```sql
-- [사전 준비] 파티션 테이블에 로컬 PK와 로컬 일반 인덱스가 있다면, 스테이징 테이블에도 1:1로 미리 생성!
CREATE UNIQUE INDEX PK_스테이징테이블 ON 스테이징테이블 (PK컬럼1, PK컬럼2);
ALTER TABLE 스테이징테이블 ADD CONSTRAINT PK_스테이징테이블 PRIMARY KEY (PK컬럼1, PK컬럼2) USING INDEX PK_스테이징테이블;

CREATE INDEX IX_스테이징테이블_N1 ON 스테이징테이블 (일반컬럼1, 일반컬럼2);

-- [파티션 교체 실행]
ALTER TABLE 파티션테이블 
EXCHANGE PARTITION 교체할파티션명 
WITH TABLE 스테이징테이블 
INCLUDING INDEXES      -- 사전 인덱스를 파티션 로컬 인덱스와 맞바꾸는 핵심 옵션
WITHOUT VALIDATION;
```

###### 3. Direct-Path INSERT (고속 병렬 적재)
CTAS를 쓸 수 없을 때, Redo를 최소화하며 기존 테이블에 밀어 넣는 문법.

```sql
-- [필수] 병렬 DML 세션 활성화
ALTER SESSION ENABLE PARALLEL DML;

-- [주의] 타겟 힌트의 별칭(T)과 소스 힌트의 별칭(S)이 쿼리의 별칭과 정확히 일치해야 함!
INSERT /*+ APPEND PARALLEL(T 4) */ INTO 타겟테이블 T (컬럼1, 컬럼2)
SELECT /*+ FULL(S) PARALLEL(S 4) */ 컬럼1, 컬럼2
FROM   소스테이블 S;

-- [필수] Direct-Path Insert 후에는 테이블에 Exclusive Lock이 걸리므로 즉시 COMMIT
COMMIT;
```

###### 4. Set-Based MERGE (단일 병합 처리)
건건이 LOOP 도는 로직을 한 방의 SQL로 튜닝.

```sql
MERGE INTO 타겟테이블 T
USING (
    -- [핵심] 1:N 조인 에러(ORA-30926) 방지를 위한 선집계 뷰
    SELECT 조인키_컬럼, 
           SUM(금액컬럼) AS SUM_AMT
    FROM   소스테이블
    GROUP BY 조인키_컬럼
) S
ON (T.조인키_컬럼 = S.조인키_컬럼)
WHEN MATCHED THEN
    UPDATE SET T.총금액 = T.총금액 + S.SUM_AMT
    -- 주의: ON 절에 쓰인 조인키 컬럼은 UPDATE SET 절에서 갱신 불가
WHEN NOT MATCHED THEN
    INSERT (조인키_컬럼, 총금액) 
    VALUES (S.조인키_컬럼, S.SUM_AMT);
```

##### ⚡ [T11] Runtime / Trace / DB Call (네트워크 통신 비용 감소)

###### 1. PL/SQL Array Processing (BULK BIND)
단일 SQL(MERGE)로 처리가 불가능한 복잡한 로직일 때, DB Call 횟수를 획기적으로 줄이는 배열 처리.

```sql
DECLARE
    -- 커서 및 컬렉션 타입 정의 (생략)
BEGIN
    OPEN 커서명;
    LOOP
        -- 1000건씩 배열에 한 번에 담아서 Fetch (DB Call 대폭 감소)
        FETCH 커서명 BULK COLLECT INTO 컬렉션변수 LIMIT 1000;
        
        -- FOR LOOP 대신 FORALL을 사용하여 배열의 데이터를 한 번에 DML 수행
        FORALL i IN 1..컬렉션변수.COUNT
            INSERT INTO 타겟테이블 VALUES 컬렉션변수(i);
            
        EXIT WHEN 커서명%NOTFOUND;
    END LOOP;
    CLOSE 커서명;
    COMMIT;
END;
```

##### 🔒 [T12] Lock / Transaction / Concurrency (동시성 제어)

###### 1. 비관적 락(Pessimistic Lock) 구문
경합이 심한 환경에서 트랜잭션 대기 시간을 직접 제어하는 문법.

```sql
-- 대기하지 않고 즉시 에러(ORA-00054) 반환
SELECT * FROM 테이블명 WHERE 조건 FOR UPDATE NOWAIT;

-- 최대 3초만 대기 후 안 풀리면 에러 반환
SELECT * FROM 테이블명 WHERE 조건 FOR UPDATE WAIT 3;

-- [실무 큐잉 처리 핵심] 락이 걸린 행은 건너뛰고 락이 없는 행만 가져옴
SELECT * FROM 테이블명 WHERE 조건 FOR UPDATE SKIP LOCKED;
```

###### 2. TM Lock (테이블 락) 방지용 인덱스
부모 테이블 데이터 삭제/수정 시, 자식 테이블 전체에 Lock이 걸려 시스템이 멈추는 것을 막는 필수 문법.

```sql
-- 자식 테이블의 외래키(FK) 컬럼에 반드시 일반 인덱스를 생성해야 함!
CREATE INDEX IX_자식테이블_FK ON 자식테이블(부모를_참조하는_FK컬럼);
```

## 3.4 패턴맵 보정 이력 · 한계 · 운영 지침


> 통합패턴맵 v2.3이 v1에서 바로잡은 개념 오류와, "SQLP 실기 필수"라고 단정하지 않는 항목들이다.
> **개념 오류 교정분은 지금도 유효한 학습 내용**이므로 보존한다.

### 4. 기존 v1의 주요 수정 사항

1. **패턴 범위 확대**
   - v1의 예시 4개 중심 구조를 15개 상위 영역과 원자/복합 패턴으로 확장.

2. **Nested Loops 설명 수정**
   - 기존: `Inner쪽에 인덱스 필수`
   - 수정: Inner 인덱스는 대표적인 효율화 수단이지만 **논리적·물리적으로 필수는 아님**. 실제 비용은 Outer 건수 × Inner Row Source 1회 처리비용과 Starts로 판단.

3. **NL Cardinality 설명 수정**
   - 기존의 `NL Outer A-Rows × NL Inner Starts` 식 표현은 부정확.
   - 수정: Outer A-Rows는 Inner Starts를 유발하는 주요 요인이며, NL 출력은 실제 조인 매칭 건수의 합으로 결정. `Starts`, `A-Rows`, 1회당 Inner 결과를 분리해서 본다.

4. **Subquery Unnesting 설명 수정**
   - 기존: EXISTS/ANY를 JOIN으로 변환하며 `SEM(H)` 처리라는 단순화.
   - 수정: Unnesting은 서브쿼리 QB를 조인 가능한 형태로 변환하는 최적화이며, 서브쿼리 의미에 따라 Semi/Anti/일반 Join 등 여러 결과가 가능. 변환 가능성은 SQL 의미와 제약에 좌우됨.

5. **Semi Join 설명 정교화**
   - `Semi Join은 중복을 제거한다`가 아니라, **내부측 중복이 외부행을 여러 번 출력시키지 않는 존재성 조인**으로 표현.

6. **FTS/PX SEND 단정 금지**
   - Full Scan 또는 PX SEND가 보인다는 사실만으로 병목으로 판정하지 않는다. 처리해야 할 데이터량, Pruning, 분배 목적, Buffers/Temp 등과 함께 판단.

7. **숙련도 임의기재 제거**
   - v1 예시의 미숙달/부분숙달 등은 실제 기록 근거가 없으므로 전부 `미평가`로 초기화.

## 3.5 표준 정답 아카이브 — 2026-09-07 출제 4문항


### 09-07 출제 4문항 표준 정답

#### 1) 문제1 — 정렬 생략 + Top-N (독립해결 96점)

```sql
CREATE INDEX IDX_ORD_02 ON TB_ORDER (BRANCH_CD, ORD_DT);   -- '=' 선두, 정렬 컬럼 후행

SELECT * FROM (
  SELECT /*+ INDEX_DESC(O IDX_ORD_02) */                   -- '정렬하지 마라'의 문자 표현
         O.ORD_NO, O.ORD_DT, O.CUST_ID, O.ORD_AMT, O.ORD_STAT
  FROM   TB_ORDER O
  WHERE  O.BRANCH_CD = 'B017'
  AND    O.ORD_DT   >= TO_DATE('20260801','YYYYMMDD')      -- TO_CHAR 가공 제거
  AND    O.ORD_DT   <  TO_DATE('20260901','YYYYMMDD')      -- 경계는 '<' (시분초 안전)
  ORDER  BY O.ORD_DT DESC )
WHERE ROWNUM <= 20;
```

**Buffers 100,253 → 24 (4,177배).**
`INDEX`는 "인덱스 써라", `INDEX_DESC`는 **"정렬하지 마라"** — 다른 힌트다.

#### 2) 문제2 — 조인통로 인덱스 + 후집계 (오답 38점)

```sql
CREATE INDEX IDX_SALES_02 ON TB_SALES (CUST_ID, SALE_DT);  -- 조인키 선두

SELECT /*+ LEADING(R C O) USE_NL(C) INDEX(C PK_CUST)
                          USE_NL(O) INDEX(O IDX_SALES_02) */
       R.CUST_ID, C.CUST_NM, COUNT(*) AS SALE_CNT, SUM(O.SALE_AMT) AS SALE_AMT
FROM   TB_CAMP_RESP R, TB_CUST C, TB_SALES O
WHERE  R.CAMP_ID  = 'C2608'
AND    C.CUST_ID  = R.CUST_ID
AND    O.CUST_ID  = R.CUST_ID
AND    O.SALE_DT >= TO_DATE('20260801','YYYYMMDD')
AND    O.SALE_DT <  TO_DATE('20260901','YYYYMMDD')
GROUP  BY R.CUST_ID, C.CUST_NM;
```

**Buffers 636,018 → 58,018 (11배).**
500만 건을 읽는 방법을 개선하려 하지 말고, **500만 건을 읽지 않는 길**을 찾는다.

#### 3) 문제3 — 세미/안티 분별 (오답 38점)

```sql
CREATE INDEX IDX_PUR_02 ON TB_PURCHASE (CUST_ID, PUR_DT);  -- 커버링 → 테이블 액세스 0회

SELECT C.CUST_ID, C.CUST_NM, C.GRADE_CD                    -- DISTINCT 불필요(PK + 비증폭)
FROM   TB_MEMBER C
WHERE  C.GRADE_CD = 'VIP'
AND    EXISTS     ( SELECT /*+ NL_SJ INDEX(P IDX_PUR_02) */ 1
                    FROM TB_PURCHASE P
                    WHERE P.CUST_ID = C.CUST_ID AND P.PUR_DT >= TRUNC(SYSDATE)-90 )
AND    NOT EXISTS ( SELECT /*+ HASH_AJ FULL(M) */ 1
                    FROM TB_CLAIM M
                    WHERE M.CUST_ID = C.CUST_ID AND M.CLAIM_DT >= TRUNC(SYSDATE)-90 );
```

**Buffers 633,200 → 123,200 (5.1배).**
핵심: **한 SQL 안의 두 서브쿼리가 서로 다른 조인 방식**을 가진다 (안쪽 600,000블록 → NL / 안쪽 3,200블록 → HASH).

#### 4) 변형 — 선집계 (미완)

```sql
CREATE INDEX IDX_SALE_02 ON TB_SALE_DTL (SALE_DT, PROD_ID, QTY, AMT);  -- 범위키 선두 + 커버링

SELECT /*+ LEADING(D P G) USE_HASH(P) USE_HASH(G) */
       P.PROD_ID, P.PROD_NM, G.CATE_NM, D.SALE_QTY, D.SALE_AMT
FROM ( SELECT /*+ NO_MERGE INDEX(D2 IDX_SALE_02) */
              D2.PROD_ID, SUM(D2.QTY) AS SALE_QTY, SUM(D2.AMT) AS SALE_AMT
       FROM   TB_SALE_DTL D2
       WHERE  D2.SALE_DT >= TO_DATE('20260801','YYYYMMDD')
       AND    D2.SALE_DT <  TO_DATE('20260901','YYYYMMDD')
       GROUP  BY D2.PROD_ID ) D,                           -- 여기서 500만 → 8만
     TB_PROD P, TB_CATEGORY G
WHERE  P.PROD_ID = D.PROD_ID
AND    G.CATE_CD = P.CATE_CD;
```

**Buffers 601,005 → 약 23,700 (25배)** + Temp 298M 소멸.
바깥 GROUP BY가 사라지는 이유: 뷰에서 이미 PROD_ID 단위로 집계했고 P·G는 PK 조인(1:1)이라 행이 늘지 않는다.
