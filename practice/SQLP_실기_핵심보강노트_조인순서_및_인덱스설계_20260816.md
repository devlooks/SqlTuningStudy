# 🧭 1. 테이블 조인 순서(Join Order) 결정 5대 패턴 바이블

SQL에서 등장하는 모든 조인 구조는 아래 5대 패턴 중 하나로 완벽히 귀결됩니다.

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│  [패턴 1] 스타형 (중심 테이블 1개 + 날개 부모 테이블들) ── 가장 흔한 실무/시험 패턴   │
│  [패턴 2] 체인형 (부모 ──> 자식 ──> 손자 직렬 연결)                            │
│  [패턴 3] 마스터-디테일 집계형 (1:N 대량 거래 집계)                           │
│  [패턴 4] Top-N 페이징형 (ORDER BY + ROWNUM)                                 │
│  [패턴 5] 특수 조인형 (Outer / Semi / Anti)                                  │
└──────────────────────────────────────────────────────────────────────────────┘
```

---

### 🏛️ [패턴 1] 스타형 (중심 테이블 + 날개 부모들) ── [출제율 50%]

중심 테이블(주문/거래/계약/배송)을 가운데 두고, 부모 테이블(고객/상품/센터/부서)들이 날개처럼 둘러싸고 있는 형태.

```text
  [부모 A : 종목/센터/상품] (20건)       [부모 B : 고객/부서] (5,000건)
            │                                    │
            │ (1:N)                              │ (1:N)
            ▼                                    ▼
       ┌──────────────────────────────────────────────┐
       │         [중심 테이블 : 주문/거래/배송]          │
       └──────────────────────────────────────────────┘
```

- **🎯 조인 순서 결정 공식:**
  **`[가장 깐깐한 부모 A (20건)]` ➡️ `[중심 테이블]` ➡️ `[나머지 부모 B]`**
- **동작 원리:**
  1. 단독 조건 건수가 가장 작은 **가장 좁은 입구(`부모 A`, 20건)**가 1등(Driving)!
  2. 부모 A의 조인 키를 들고 **`중심 테이블`**로 진입하여 데이터를 팍 줄임 (80,000건 -> 200건)!
  3. 줄어든 200건만 들고 반대편 **`부모 B`**의 PK를 200번만 콕콕 확인 (`Starts=200`).
- **표준 힌트:** `/*+ LEADING(부모A 중심테이블 부모B) USE_NL(중심테이블) USE_NL(부모B) */`

---

### ⛓️ [패턴 2] 체인형 (직렬 연결: 부모 ➡️ 자식 ➡️ 손자) ── [출제율 20%]

테이블들이 1열로 줄줄이 연결된 구조. (예: `고객 ➡️ 주문 ➡️ 주문상세 ➡️ 배송`)

```text
[고객 (부모)] ──(1:N)──> [주문 (자식)] ──(1:N)──> [주문상세 (손자)] ──(1:1)──> [배송]
```

- **🎯 조인 순서 결정 공식:**
  > **"체인 상에서 '가장 강력한 필터(최소 건수)'가 걸려 있는 노드에서 출발하여 양옆으로 전파한다!"**
- **Case A (고객 쪽에 '특정 VIP 1명' 조건이 걸린 경우):**
  - 순서: `고객(1명)` ➡️ `주문` ➡️ `주문상세` ➡️ `배송` (Top-Down)
- **Case B (주문상세 쪽에 '특정 이벤트 상품 1개' 조건이 걸린 경우):**
  - 순서: `주문상세(10건)` ➡️ `주문` ➡️ `고객` ➡️ `배송` (Bottom-Up)

---

### 📊 [패턴 3] 마스터-디테일 집계형 (1:N 대량 거래 집계) ── [출제율 15%]

마스터(고객 5,000명)와 대량 거래(거래 150만 건)를 조인하여 `SUM/COUNT` 집계하는 경우.

- **🎯 조인 순서 및 방식 공식:**
  > **"조인 대상 건수가 수만~수십만 건 이상이면 NL 조인의 Random I/O는 무너진다. HASH JOIN 또는 선집계 뷰를 사용하라!"**
- **해법 1 (Hash Join):**
  - 작은 테이블을 Build Input(해시 맵), 대량 테이블을 Probe Input으로 결합.
  - `/*+ LEADING(고객 거래) USE_HASH(거래) */`
- **해법 2 (선집계 인라인 뷰):**
  - 거래 테이블을 인라인 뷰에서 `GROUP BY`로 먼저 축약한 뒤 고객과 조인!

---

### 🏎️ [패턴 4] Top-N 페이징형 (`ORDER BY + ROWNUM <= N`) ── [출제율 10%]

화면에서 가장 최근 데이터 10~20건만 빠르게 먼저 보여주어야 하는 부분범위 처리.

- **🎯 조인 순서 결정 공식:**
  > **"건수 크기와 무관하게, `ORDER BY` 정렬 인덱스를 가진 테이블이 무조건 1등(Driving)!"**
- 전체 주문이 500만 건이어도, 일자 인덱스를 거꾸로 읽으며 조건을 만족하는 10건을 채우면 **쿼리가 즉시 멈춤(COUNT STOPKEY)**!
- `/*+ LEADING(정렬인덱스보유테이블 타테이블) USE_NL(타테이블) */`

---

### 🛡️ [패턴 5] 특수 조인형 (Outer / Semi / Anti) ── [출제율 5%]

1. **`LEFT OUTER JOIN`:**
   - 기준 테이블(보존되어야 하는 Left 테이블)이 **무조건 1등(Driving)**! (순서 뒤집기 불가)
2. **`EXISTS` (Semi-Join):**
   - 1:N 조인 증폭 및 `DISTINCT` 부하를 제거하고, 1건만 찾으면 즉시 멈추는 **Short-Circuit(조기 종료)** 실현!
   - `/*+ LEADING(메인 서브Q) USE_NL(서브Q) */` 또는 `/*+ UNNEST NL_SJ */`

# 📐 2. 결합 인덱스 설계의 황금 공식

인덱스를 설계할 때는 아래 **4단 서랍 공식**을 기계처럼 적용합니다.

**인덱스 컬럼 순서 = [ = 조건 컬럼들 ] + [ 조인 연결고리 키 ] + [ 범위(Between, <, >) 조건 ] + [ ORDER BY 정렬 컬럼 전수 ]**

### 💡 인덱스 설계 핵심 원리 2가지
1. **등치(`=`) 조건 컬럼들의 순서 불변성:**
   - `=` 조건 컬럼들끼리는 인덱스 내에서 순서가 앞뒤로 바뀌어도 **스캔 범위와 I/O가 100% 동일함!**
   - 예: `(CENTER_CD, SEND_DT, DELIV_STAT, ...)` == `(CENTER_CD, DELIV_STAT, SEND_DT, ...)` (둘 다 만점)
2. **정렬 생략(Stopkey)을 위한 완전성:**
   - `ORDER BY 일자 DESC, 시간 DESC`에서 `시간` 컬럼이 인덱스에서 누락되면, 동일 일자 내 시간 정렬이 깨지므로 **오라클은 `SORT` 연산을 강제로 돌려버림!** (반드시 정렬 컬럼 몽땅 포함할 것)

# 📊 3. Starts vs A-Rows 판독 및 조인 메소드(NL vs HASH) 선택 기준

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│  🔹 선행 집합이 [수 건 ~ 수천 건 이하 (소량)]  ➡️  무조건 NL JOIN (USE_NL)     │
│  🔹 선행 집합이 [수만 건 ~ 수십만 건 이상 (대량)] ➡️  무조건 HASH JOIN (USE_HASH)  │
└─────────────────────────────────────────────────────────────────────────────┘
```

- **NL Join (Single Block Random I/O):**
  - 소량 건수(5건, 100건)에 대해 후행 테이블 인덱스를 몇 번만 콕콕 찍을 때 최적 (메모리 사용 없음, 첫 행 즉시 출력).
- **Hash Join (Multi-Block Sequential I/O + PGA):**
  - 대량 건수(50만 건) 조인 시 Random Access 부하를 없애고 메모리 해시 맵으로 고속 매칭.
- **Starts의 비밀:**
  - 상위 노드의 `A-Rows`(출력 건수)가 하위/내부 노드의 `Starts`(루프 반복 횟수)가 됨.
  - 시험 답안 병목 서술 시: *"선행 테이블 A-Rows N건으로 인해 후행 테이블 탐색이 N회 반복(Starts=N)되어 M건의 Random Access I/O 병목이 발생함"*으로 서술.

### (1) 서브쿼리 제어 3대 힌트 세트 공식

```text
┌────────────────────────────────────────────────────────────────────────────────────────┐
│ 1. 서브쿼리를 조인(Semi-Join)으로 풀어서 처리할 때:                                         │
│    👉 /*+ UNNEST NL_SJ */   또는   /*+ UNNEST HASH_SJ */                               │
│                                                                                        │
│ 2. 서브쿼리를 절대 풀지 않고 메인 쿼리 뒤에서 FILTER로 남길 때:                              │
│    👉 /*+ NO_UNNEST */                                                                 │
│                                                                                        │
│ 3. 조인이 많은 쿼리에서 서브쿼리 FILTER를 조인 중간에 가장 먼저 적용하고 싶을 때:             │
│    👉 /*+ NO_UNNEST PUSH_SUBQ */                                                      │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

---

### (2) 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN` 1회 집계 변환 공식

1. **스칼라의 본질은 `LEFT OUTER JOIN`:**
   - 상대 테이블 매칭 데이터가 없으면 `NULL`을 반환하는 특성이 있으므로, 조인 변환 시 반드시 **`LEFT OUTER JOIN`**을 사용하여 메인 집합의 유실을 방지한다.
2. **동일 테이블 중복 스캔 제거 (`CASE WHEN` 1회 집계):**
   - 동일 테이블에 대해 정상금액(`SUM`)과 반품건수(`COUNT`)를 각각 스칼라로 쪼개지 말고, **단 1개의 인라인 뷰에서 `CASE WHEN`으로 동시에 집계**한다.
   - 금액 합계: `SUM(CASE WHEN 조건 THEN 금액 END)`
   - 건수 카운트: `COUNT(CASE WHEN 조건 THEN 1 END)`
3. **대량 결합은 `USE_HASH`:**
   - 메인 데이터가 수만 건 이상이고, 선집계된 인라인 뷰(`V`)에는 B-Tree 인덱스가 없으므로 **무조건 `USE_HASH(V)`**를 지정한다.

### (3) [오라클 공식 규정] 뷰 머징(View Merging) 원천 불가 8대 제약사항

아래 항목이 인라인 뷰 내에 포함되어 있으면, 오라클은 힌트와 무관하게 **뷰 머징을 100% 포기하고 무조건 독립적인 `VIEW` 오퍼레이션으로 실행**합니다:

| 번호 | 제약 요소 | 상세 설명 및 예시 |
|:---:|---|---|
| **1** | **`ROWNUM` 의사컬럼** | `WHERE ROWNUM <= 10` 등 Top-N 페이징 처리가 들어간 뷰 |
| **2** | **집합 연산자 (Set Operators)** | `UNION`, `UNION ALL`, `INTERSECT`, `MINUS`가 사용된 뷰 |
| **3** | **계층형 쿼리 (Hierarchical Query)** | `START WITH`, `CONNECT BY` 절이 포함된 계층형 뷰 |
| **4** | **`GROUP BY` 없는 집계 함수** | `SELECT SUM(AMT), AVG(QTY) FROM ...` 처럼 전체 단 1행만 반환하는 스칼라 집계 뷰 |
| **5** | **분석/윈도우 함수 (Analytic Functions)** | `ROW_NUMBER()`, `RANK()`, `SUM() OVER (...)` 등이 포함된 뷰 |
| **6** | **`MODEL` 절** | 오라클 다차원 모델링 `MODEL` 구문이 사용된 뷰 |
| **7** | **시퀀스 및 비결정적 함수** | 뷰의 SELECT 목록에 `SEQ.NEXTVAL` 또는 비결정적(Non-deterministic) 함수 포함 시 |
| **8** | **XMLTable / Flashback 절** | `XMLTABLE(...)` 구문 또는 `AS OF TIMESTAMP/SCN` 과거 시점 조회가 포함된 뷰 |

---

### (4) [튜너의 무기] 튜너가 직접 `/*+ NO_MERGE */`를 거는 5대 실무 목적

오라클이 머징을 시도할 수 있는 상황에서, 성능을 위해 튜너가 의도적으로 머징을 차단하는 핵심 케이스:

1. **[선집계 강제]** `GROUP BY`로 수천만 건을 수만 건으로 먼저 축소한 뒤 메인과 결합할 때 (Complex View Merging 방지).
2. **[선중복제거]** `DISTINCT`로 대량 집합의 중복을 먼저 깎아낸 뒤 조인할 때.
3. **[조인순서 통제]** 5~6개 복잡한 테이블 조인 시 인라인 뷰를 '독립 블록'으로 묶어 `LEADING` 순서를 통제할 때.
4. **[조인증폭 방지]** 1:N:M 관계에서 중간 카디널리티 폭발(데카르트곱)을 막고 싶을 때.
5. **[함수호출 지연]** 무거운 PL/SQL 사용자 정의 함수 호출을 최종 10건 필터링 뒤로 미루어 호출 횟수를 극소화할 때.

### 📋 [문제 1] 스칼라 서브쿼리 ➡️ `LEFT OUTER JOIN` + `CASE WHEN` 1회 집계 + `USE_HASH`

* **상황:** 배송기사 15,000명(`TB_DRIVER`)에 대해 프로필(`TB_DRIVER_PROFILE`)과 1,500만 건 배송이력(`TB_DELIVERY_LOG`)의 완료금액(`SUM`)과 실패건수(`COUNT`)를 각각 스칼라로 조회하여 45,000회 I/O 폭발.

#### 💯 [만점 정답 SQL]
```sql
SELECT /*+ LEADING(D P V) USE_NL(P) USE_HASH(V)
           INDEX(D IX_DRIVER_01) INDEX(P PK_TB_DRIVER_PROFILE) */
       D.DRIVER_ID,
       D.DRIVER_NM,
       P.CAR_TYPE_CD,
       NVL(V.DONE_FEE_AMT, 0) AS DONE_FEE_AMT,
       NVL(V.FAIL_CNT, 0)     AS FAIL_CNT
  FROM TB_DRIVER D
  LEFT OUTER JOIN TB_DRIVER_PROFILE P 
    ON P.DRIVER_ID = D.DRIVER_ID
  LEFT OUTER JOIN (
       SELECT /*+ NO_MERGE INDEX(L IX_DELIV_01) */
              L.DRIVER_ID,
              SUM(CASE WHEN L.DELIV_STAT_CD = 'DONE' THEN L.DELIV_FEE ELSE 0 END) AS DONE_FEE_AMT,
              COUNT(CASE WHEN L.DELIV_STAT_CD = 'FAIL' THEN 1 END)                AS FAIL_CNT
         FROM TB_DELIVERY_LOG L
        WHERE L.DELIV_DT >= '20260101'
        GROUP BY L.DRIVER_ID
  ) V
    ON V.DRIVER_ID = D.DRIVER_ID
 WHERE D.AREA_CD = 'SEOUL'
   AND D.JOIN_DT >= '20260101';
```

### 📋 [문제 3] 서브쿼리 조기 필터링 (`PUSH_SUBQ` vs `UNNEST NL_SJ`)

* **상황:** 당일 예약자 10,000건(`TB_RESERV`)에 대해 진료과(`TB_DEPT`)와 의사(`TB_DOCTOR`)를 20,000회 헛조인한 뒤, 맨 마지막에 당일 중증 응급로그(`TB_EMERGENCY_LOG`, 단 20건)로 거르는 비효율 해소.

#### 💯 [방식 1: PUSH_SUBQ 정답 (서브쿼리 안에 힌트 추가)]
```sql
SELECT R.RESV_NO, R.PATIENT_ID, D.DEPT_NM, DOC.DOC_NM
  FROM TB_RESERV R, TB_DEPT D, TB_DOCTOR DOC
 WHERE R.DEPT_CD = D.DEPT_CD AND R.DOC_ID = DOC.DOC_ID
   AND R.RESV_STAT_CD = '01' AND R.RESV_DT = '20260817'
   AND EXISTS (
       SELECT /*+ NO_UNNEST PUSH_SUBQ INDEX(E IX_EMRG_01) */ 1
         FROM TB_EMERGENCY_LOG E
        WHERE E.PATIENT_ID = R.PATIENT_ID
          AND E.EMRG_LEVEL = 'L1'
          AND E.LOG_DT >= '20260817'
   );
```

#### 💯 [방식 2: UNNEST NL_SJ 정답 (메인 LEADING 2순위에 E 배치)]
```sql
SELECT /*+ LEADING(R E D DOC) USE_NL(E) NL_SJ(E) USE_NL(D) USE_NL(DOC)
           INDEX(R IX_RESV_01) INDEX(E IX_EMRG_01) 
           INDEX(D PK_TB_DEPT) INDEX(DOC PK_TB_DOCTOR) */
       R.RESV_NO, R.PATIENT_ID, D.DEPT_NM, DOC.DOC_NM
  FROM TB_RESERV R, TB_DEPT D, TB_DOCTOR DOC
 WHERE R.DEPT_CD = D.DEPT_CD AND R.DOC_ID = DOC.DOC_ID
   AND R.RESV_STAT_CD = '01' AND R.RESV_DT = '20260817'
   AND EXISTS (
       SELECT /*+ UNNEST */ 1
         FROM TB_EMERGENCY_LOG E
        WHERE E.PATIENT_ID = R.PATIENT_ID
          AND E.EMRG_LEVEL = 'L1'
          AND E.LOG_DT >= '20260817'
   );
```
